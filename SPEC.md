# ТЗ: Little Snitch VPN Companion

macOS-приложение, которое следит за **фактическим egress** машины и при утечке трафика мимо
VPN автоматически включает запрещающие rule groups в Little Snitch. Восстановилось — выключает.

**Статус: согласовано 2026-07-29, готово к реализации.** Документ самодостаточен: исполнитель
(агент в отдельной сессии/репозитории) должен суметь построить приложение только по нему.
Все технические факты, помеченные «проверено», сняты с целевой машины 2026-07-29.

---

## 0. TL;DR для исполнителя

- Строим меню-бар-приложение на Swift/SwiftUI (min macOS 26) + привилегированный helper
  (`SMAppService.daemon` + XPC), который единственный вызывает `littlesnitch` CLI (root).
- Детектор — только фактический egress через маяк Cloudflare (`warp=on` = защищён),
  три слоя: постоянное соединение-«растяжка», события сетевого пути, периодические пробы.
- Ядро — доменная state machine (§5), пишется первой, через TDD.
- UI собирается по дизайн-системе (§8) и макетам `design/app.pen`.
- Порядок работ — §12, приёмка — §14. Решения по всем развилкам уже приняты (§2) —
  не перерешивать.

## 1. Контекст и задача

Окружение пользователя (важно для понимания; секретов здесь нет):

- Личный MacBook (Apple Silicon, macOS 26.5.2 — проверено `sw_vers`).
- Foreign-трафик машины в норме уходит через VPN-цепочку и выходит в интернет через
  Cloudflare WARP. Защита обеспечивается **одним из двух способов**: VPN-клиент Happ на
  самом Маке (вне дома) ИЛИ прозрачный VPN на домашнем роутере (дома, клиент на Маке
  выключен). Приложению **всё равно, кто защищает** — критерий один: что видит внешний маяк.
- РУ-трафик намеренно идёт напрямую (сплит на стороне VPN) — приложение не должно ему мешать.
- Little Snitch (6-я версия) куплен и установлен: `/Applications/Little Snitch.app`.

**Инвариант, ради которого всё строится:** приложения из «запрещённого» списка (Claude,
все JetBrains IDE, Android Studio — список живёт в Little Snitch и управляется пользователем)
никогда не выходят в сеть напрямую, мимо VPN.

Следствия-требования:

1. Утечка обнаружена → запрещённым закрыть сеть (через LS), уведомить.
2. Egress вернулся в норму → блок снять автоматически, без участия человека.
3. Запрещённое приложение не запущено → отвал VPN ничему не мешает (deny-правило на
   незапущенное приложение — no-op). Никакого «рубить всё».
4. Незапрещённые приложения и РУ-трафик работают всегда, Мак остаётся онлайн.
5. Дома и в гостях поведение одинаковое.

## 3. Терминология

| Термин | Значение |
|---|---|
| **Protected** | Маяк ответил, `warp=on`/`warp=plus`, либо `ip` ∈ `EXPECTED_IPS` |
| **Leak** | Маяк ответил и распарсен, но egress чужой (warp=off, ip не из ожидаемых) |
| **Offline** | Маяк недоступен или ответ не парсится (нет сети, captive portal) — НЕ утечка |
| **Paused** | Пользователь поставил мониторинг на паузу |
| **Маяк** | Внешний endpoint, возвращающий egress-IP и флаг WARP |
| **РУ-маяк** | Сервис в зоне `.ru`, отвечающий IP клиента; из-за РУ-сплита запрос идёт напрямую, ответ = «прямой IP» текущей сети |
| **Прямой IP** | IP, с которого машина сейчас ходит на РУ-ресурсы напрямую; динамическая часть запрещённого списка |
| **`FORBIDDEN_EGRESS`** | «Запрещённый egress»: IP, появление которых в egress = утечка независимо от прочих признаков (серверы пользователя + прямой IP) |
| **Растяжка** | Постоянное TLS-соединение к маяку; его обрыв — мгновенный сигнал |
| **Reconcile** | Приведение фактического состояния групп LS к целевому для текущего состояния |

## 4. Детекция

### 4.1. Маяк

- Основной: `https://www.cloudflare.com/cdn-cgi/trace`
- Резервный: `https://1.1.1.1/cdn-cgi/trace` (по IP — не зависит от DNS)

Формат ответа — plain text `key=value` по строкам. Значимые поля: `ip=`, `warp=`
(`off`/`on`/`plus`); полезные для UI: `colo=`, `loc=`. **Проверено с целевой машины
через защищённую цепочку:** `ip=2a09:bac5:…` (Cloudflare), `colo=AMS`, `loc=NL`, `warp=on`.

Критерий «защищён» — **оба условия сразу**:

1. `warp ∈ {on, plus}` ИЛИ `ip ∈ EXPECTED_IPS` (allowlist, по умолчанию пуст);
2. `ip ∉ FORBIDDEN_EGRESS` — denylist «запрещённый egress» (§4.5): статический список
   серверов инфраструктуры + динамический прямой РУ-IP.

Запрещённый список сильнее всего остального: egress из него = Leak даже при `warp=on`.
Диагноз в журнале/уведомлении уточняется по источнику совпадения:

- ip из статического списка серверов → «цепочка вышла напрямую с сервера <ip>» —
  обычно означает, что на выходном узле отвалился WARP и наружу светится IP датацентра;
- ip == прямой РУ-IP → «полный обход VPN: foreign-трафик идёт с прямого IP сети».

Классификация результата пробы:

| Ответ | Результат |
|---|---|
| HTTP 200, есть `ip=`, ip ∈ FORBIDDEN_EGRESS (любой `warp=`) | leak-кандидат, диагноз по источнику |
| HTTP 200, есть `ip=`, `warp=on/plus`, ip ∉ FORBIDDEN_EGRESS | protected |
| HTTP 200, есть `ip=`, `warp=off`, ip ∈ EXPECTED_IPS, ip ∉ FORBIDDEN_EGRESS | protected |
| HTTP 200, есть `ip=`, `warp=off`, ip чужой | leak-кандидат |
| Таймаут / сетевой сбой / TLS-ошибка / ответ без `ip=` (captive portal) | offline |

### 4.2. Три слоя детектора

1. **Растяжка** — `NWConnection` (TLS) к маяку. Раз в 15 с по этому же соединению
   уходит минимальный `GET /cdn-cgi/trace HTTP/1.1` + `Connection: keep-alive`; дедлайн
   чтения ответа 5 с. Любой обрыв (EOF/RST/ошибка) или дедлайн → немедленная свежая проба.
   Чистый long-poll невозможен: edge Cloudflare рвёт висящие соединения по idle-таймауту —
   heartbeat это и обходит, и превращает соединение в проверку живости. Переустановка
   растяжки после обрыва — с экспоненциальным backoff (2 с → 4 → 8 → … максимум 60 с),
   чтобы не молотить сеть в офлайне.
2. **События пути** — `NWPathMonitor`: любое изменение (интерфейсы, шлюз, появление или
   исчезновение utun) → немедленная проба (debounce ~300 мс от шквала событий).
3. **Плановая свежая проба** — раз в 60 с, отдельным новым соединением: `URLSession`
   с ephemeral-конфигурацией (без кэша и переиспользования соединений), таймаут 6 с.

Зачем все три (проверено рассуждением и опытом, не удалять ни один):

- обрыв туннеля обычно активно убивает растяжку (перехватчик терминировал TCP на себе) —
  ловится мгновенно;
- НО VPN может отвалиться, не убив установленное соединение: маршруты перевернулись,
  старый поток доживает по старому пути, а **новые** соединения уже идут напрямую.
  Растяжка молчит — утечку видит только свежая проба. Поэтому пробы обязательны;
- обратный безвредный случай: упал апстрим VPN при живом туннеле — растяжка виснет,
  но утечки нет (трафик в «чёрной дыре» туннеля) → это Offline, группы не трогаем.

### 4.3. Подтверждение и задержки

Переход в Leak — **только после двух** leak-проб подряд с интервалом 2–3 с (защита от
разовых ложняков). Protected подтверждения не требует.

| Сценарий отвала | Чем ловится | Задержка обнаружения |
|---|---|---|
| Туннель умер, соединению RST | растяжка | < 1 с |
| Маршруты перевернулись (выкл. VPN, смена сети) | путь + растяжка | ~1–2 с |
| Путь тихо завис при живом туннеле | heartbeat-дедлайн | ≤ ~20 с (это Offline, не Leak) |
| Старый поток жив, новые текут мимо | плановая проба | ≤ ~60 с |

### 4.4. РУ-маяк: автоопределение прямого IP

Зачем: РУ-трафик по сплиту идёт напрямую, поэтому сервис в зоне `.ru` всегда видит
**реальный IP текущей сети** (дома — провайдера, в гостях — чужой сети, на мобильном —
оператора). Этот адрес по определению никогда не должен оказаться egress'ом foreign-маяка —
он автоматически попадает в динамическую часть `FORBIDDEN_EGRESS`.

- Запрос: конфигурируемые URL; **домен обязан быть в зоне `.ru`** — иначе запрос уйдёт
  через VPN и вернёт не то. HTML-парсинг не нужен, оба маяка отдают чистый формат
  (**проверено с целевой машины 2026-07-29**):
  - основной: `https://yandex.ru/internet/api/v0/ip` — HTTP 200, `application/json`,
    тело — JSON-строка `"<ip>"`;
  - резервный: `https://2ip.ru` — для не-браузерного клиента отдаёт `text/plain`, голый IP
    (поведение зависит от User-Agent: слать явный curl-подобный UA, не браузерный).
  Ответ в любом случае валидировать: тело после разбора обязано быть IP-адресом (v4/v6),
  иначе результат отбрасывается. URLSession ephemeral, таймаут 6 с.
  Не годятся (проверено): `myip.ru` (IP рендерится скриптом), `api.2ip.ru`, `ip.rt.ru`
  (не существуют). Оба рабочих endpoint'а неофициальные — потому их два и оба
  конфигурируемы.
- Когда: при старте, при каждом событии сети (вместе с основной пробой), далее раз в
  `ruBeaconRefreshSeconds` (300 с). Ответ живёт до следующей смены сети — мобильный CGNAT
  меняет адрес часто.
- Прямой IP обновился → немедленная свежая проба foreign-маяка (переоценка состояния).
- **Guard от вырожденного случая**: если ответ РУ-маяка совпал с текущим protected-egress
  (`warp=on`) — значит `.ru` не в сплите и запрос ушёл через VPN. Такой ответ в denylist
  НЕ добавлять, в журнал — предупреждение «РУ-маяк прошёл через VPN, сплит не работает?».
- Сбой РУ-маяка состояний не меняет: динамическая запись просто устаревает (в UI — давность).

### 4.5. ⚠️ Чего НЕ делать (проверенные грабли)

- **Не использовать статус VPN-клиента** (`scutil --nc status`) как детектор: клиент
  поднимает туннельный интерфейс, не дожидаясь ответа сервера — «Подключено» ничего не
  говорит о реальном пути трафика. Допустимо показывать в UI как справку, не более.
- **Не определять «активность» приложений через `lsof -sTCP:ESTABLISHED`**: у Electron/HTTP2-
  приложений (проверено на Claude) сокеты между запросами видны в состоянии `CLOSED`,
  established-снимок пуст даже при активной работе. Механизм LS делает критерий активности
  ненужным (deny-правило на незапущенное приложение — no-op).

## 5. Состояния и переходы (ядро домена)

Состояния: `Protected`, `Leak`, `Offline`, `Paused`. Плюс флаг «helper недоступен».

| Из | Событие | В | Действия |
|---|---|---|---|
| любое (кроме Paused) | проба ×2 = чужой egress | Leak | reconcile: включить группы по маппингу; уведомление |
| Leak | проба = защищён | Protected | reconcile: выключить группы; уведомление |
| Protected | обрыв растяжки / событие пути | — | немедленная проба → по результату |
| Protected/Leak | пробы не отвечают | Offline | группы НЕ трогать |
| Offline | проба ответила | Protected или Leak | по результату + reconcile |
| любое | пользователь: Пауза | Paused | группы НЕ трогать; детектор остановить |
| Paused | пользователь: Возобновить | по пробе | немедленная проба + reconcile |
| Leak | helper не отвечает | Leak | эскалация (ФТ-9), если включена |
| старт приложения | — | по пробе | немедленная проба + reconcile |

Принципы:

- **Reconcile, а не история.** При каждом переходе и на старте приложение сверяет
  фактическое состояние групп LS с целевым для текущего состояния и приводит к нему.
  Никогда не полагаться на «мы же включали». Повторное включение включённой группы —
  допустимая no-op операция.
- Все действия идемпотентны; ошибка применения не меняет состояние детектора, но
  показывается (уведомление + журнал) и взводит флаг «helper недоступен».

## 6. Функциональные требования

- **ФТ-1. Мониторинг egress.** Детектор §4, состояния §5. Мониторинг активен с запуска;
  появление любой сети → немедленная проба.
- **ФТ-2. Реакции.** Настраиваемый маппинг «состояние → какие rule groups включены».
  По умолчанию: Leak → включить выбранные группы; Protected → выключить. Offline/Paused →
  ничего не менять. Применение — через reconcile (§5).
- **ФТ-3. Список групп из LS.** Приложение получает список rule groups (имя + текущее
  состояние) через helper (`littlesnitch export-model`, §9) и отображает в настройках
  с чекбоксом «включать при утечке» у каждой. Обновление: при открытии вкладки и кнопкой
  «Обновить список из LS».
- **ФТ-4. Меню-бар.** `MenuBarExtra` (window-стиль), без Dock (`LSUIElement`). Иконка —
  состояние (§7.5). Состав поповера — §7.1.
- **ФТ-5. Уведомления** (`UserNotifications`): утечка обнаружена (+какие группы включены);
  защита восстановлена; helper/LS недоступен; ошибка переключения группы. Две отключаемые
  категории: «утечка и восстановление», «ошибки».
- **ФТ-6. Журнал.** Каждое событие: время, триггер (растяжка/путь/проба/ру-маяк/helper/пользователь),
  egress-IP, событие (переход состояний или факт), действие (что сделали с группами).
  Окно с фильтром (Все/Переходы/Действия/Ошибки), экспорт в текст, очистка. Хранение:
  JSONL в `~/Library/Application Support/LittleSnitchVPNCompanion/journal.jsonl`,
  ротация 7 дней.
- **ФТ-7. Настройки** (окно с вкладками Общие/Детектор/Группы — состав §7.2–7.4).
  Хранение — `UserDefaults`. Ключи: `launchAtLogin`, `monitoringEnabled`, `observeOnly`,
  `escalationEnabled`, `notifyTransitions`, `notifyErrors`, `heartbeatSeconds`,
  `probeSeconds`, `probeTimeoutSeconds`, `expectedIPs` ([String]), `leakGroups` ([String]),
  `forbiddenEgressIPs` ([String], статическая часть denylist), `ruBeaconURL`,
  `ruBeaconRefreshSeconds`. Динамический прямой IP в defaults не хранится (runtime,
  сбрасывается при смене сети).
- **ФТ-8. Автозапуск.** Login item через `SMAppService`, тумблер в настройках, включается
  в онбординге.
- **ФТ-9. Эскалация.** Если Leak подтверждён, а helper недоступен или CLI вернул ошибку —
  выключить Wi-Fi: `networksetup -setairportpower <dev> off` (root НЕ нужен; Wi-Fi-девайс
  определять через `networksetup -listallhardwareports`, на целевой машине это `en0`).
  Уведомление с объяснением. По умолчанию включена.
- **ФТ-10. Режим наблюдения** (`observeOnly`): детектор и журнал работают, уведомления
  показываются, но группы LS и Wi-Fi не трогаются. Для обкатки.
- **ФТ-11. Онбординг** при первом запуске (§7.6): helper, группа в LS, уведомления.

## 9. Интеграция с Little Snitch (факты проверены на целевой машине)

- CLI: `/Applications/Little Snitch.app/Contents/Components/littlesnitch`.
- **Работает только под root** — обычному пользователю отвечает
  `littlesnitch must be run as root!` (проверено на `export-model` и `rulegroup`).
  Отсюда обязательность helper-демона.
- Используемые команды:
  - `littlesnitch rulegroup -e <имя>` / `-d <имя>` — включить/выключить rule group или
    blocklist. Основной рабочий инструмент.
  - `littlesnitch export-model` — JSON всей модели правил. Источник списка групп (имена +
    enabled-состояние для reconcile). Модель может быть большой — парсить выборочно,
    наружу отдавать только имена и статусы. Точную структуру JSON исполнителю посмотреть
    на месте (формат не документирован).
  - `littlesnitch log-traffic` — лог соединений (задел на будущее, §16).
  - Флаг `-u <user>` — выполнение от имени пользователя (актуально при вызове из
    root-демона, если команде нужен пользовательский контекст).
- `profile -a <имя>` / `-d` существует, но НЕ используется (решение №3: механизм — rule
  groups; профили — другой механизм LS, взаимоисключающие наборы).
- Группы и правила создаёт/правит только пользователь в UI LS. Приложение никогда не
  модифицирует правила — только enable/disable групп по имени.
- Исполнителю проверить на месте: коды возврата `rulegroup` (повторное включение
  включённой группы; несуществующее имя) и структуру `export-model`.
- Деградация: CLI отсутствует/ошибка/таймаут (>3 с) → флаг «helper недоступен»,
  уведомление, при Leak — эскалация (ФТ-9). Формат может меняться с версиями LS —
  при неудаче парсинга внятная ошибка, не падение.

### 10.1. Слои (Clean Architecture + DDD, зависимости только внутрь)

- **Domain** (чистый Swift, без Apple-фреймворков): `EgressState`, `ProbeResult`,
  `ProbeTrigger`, `LeakPolicy`, `RuleGroup`, `RuleGroupMapping`, `StateMachine` (таблица §5),
  `JournalEvent`. Полностью покрывается unit-тестами.
- **Application**: use cases — `EvaluateProbe`, `ApplyPolicy` (reconcile), `SyncRuleGroups`,
  `PauseMonitoring`, `ResumeMonitoring`, `RunProbeNow`, `HandleHelperFailure` (эскалация).
  Порты (протоколы): `BeaconProbing`, `DirectIPProbing` (РУ-маяк), `TripwireMonitoring`,
  `PathMonitoring`, `RuleGroupGateway`, `WifiPowerGateway`, `NotificationPresenting`,
  `JournalStore`, `SettingsStore`, `Clock`.
- **Infrastructure**: `CloudflareBeaconProber` (URLSession ephemeral),
  `RuBeaconProber` (прямой IP, §4.4),
  `TripwireConnection` (Network.framework), `SystemPathMonitor` (NWPathMonitor),
  `HelperRuleGroupGateway` (XPC-клиент), `NetworksetupWifiGateway`,
  `UserNotificationsPresenter`, `FileJournalStore` (JSONL, ротация 7 дней),
  `DefaultsSettingsStore`.
- **Presentation**: SwiftUI — `MenuBarExtra`, окна Настройки/Журнал/Онбординг, MVVM поверх
  use cases. Дизайн-система §8 — отдельный модуль (токены + атомы + молекулы, имена как
  в макетах).

### 10.2. Привилегированный helper

- Отдельный таргет-демон, регистрируется через `SMAppService.daemon(plistName:)`; plist
  в бандле (`Contents/Library/LaunchDaemons/dev.sunnyday.lsvpncompanion.helper.plist`)
  с `BundleProgram` и `MachServices` = `dev.sunnyday.lsvpncompanion.helper`. Одобрение —
  System Settings → Login Items (шаг 1 онбординга).
- XPC-контракт (узкий, произвольные команды не проходят по построению):

```swift
@objc protocol HelperProtocol {
    func version(reply: @escaping (String) -> Void)
    func listRuleGroups(reply: @escaping (Data?, String?) -> Void)   // JSON [{name, enabled}]
    func setRuleGroup(_ name: String, enabled: Bool,
                      reply: @escaping (Bool, String?) -> Void)
}
```

- Безопасность: helper валидирует XPC-клиента по code-signing requirement (audit token →
  `SecCodeCopyGuestWithAttributes`; requirement — тот же сертификат + bundle id приложения).
  Helper знает единственный путь к `littlesnitch` и три операции. Таймаут на вызов CLI 3 с.
- Подпись: приложение и helper — одним самоподписанным сертификатом (Keychain Access →
  Certificate Assistant → Create a Certificate, тип Code Signing). App Sandbox **выключен**
  у обоих таргетов; Hardened Runtime включить, если не мешает локальной подписи.

## 12. План работ для исполнителя

1. **Скелет**: таргеты app + helper, слои, DI, самоподписанная подпись, `LSUIElement`,

2. **Domain через TDD**: `StateMachine` + `LeakPolicy` + тесты таблицы §5 — до UI.
3. **Инфраструктура детектора**: пробер → растяжка → path monitor; интеграционная проверка
   на живой машине (сеть без VPN → leak-кандидат).
4. **Helper + XPC**: установка, валидация клиента, `rulegroup`/`export-model`; проверить

5. **Reconcile + уведомления + журнал.**
6. **UI**: дизайн-система (токены → атомы → молекулы), затем экраны §7; онбординг.
7. **Приёмка §14**; сутки обкатки в `observeOnly`, затем боевой режим.

## 15. Риски и ограничения (приняты осознанно)

- **Окно обнаружения**: худший случай — «старый поток жив, новые текут» — до ~60 с
  (плановая проба). Типовые отвалы — секунды.
- **Слепое пятно**: меряется путь маяка, а не каждый поток; частичная поломка сплита
  (утечка отдельных направлений при живом маяке) не видна. Границу не расширяем.
- **Captive portal** = Offline: группы не трогаются (сети всё равно нет), утечкой не считается.
- **Зависимость от Cloudflare**: маяки недоступны → Offline (safe-состояние). Свой маяк
  решено не поднимать.
- **Сторонние РУ-маяки** (yandex internetometer API, 2ip.ru): endpoints неофициальные,
  могут исчезнуть или сменить формат. Митигация: два кандидата, оба конфигурируемы,
  ответ валидируется как IP; сбой некритичен (динамическая запись denylist просто
  устаревает).
- **Формат LS**: CLI/`export-model` могут измениться с обновлением LS — деградация с
  внятной ошибкой; версии helper и CLI показывать в UI.
- Самоподписанная подпись валидна только локально; при переносе на другую машину —
  пересоздать сертификат и переподписать (приемлемо: машина одна).
- Первое уведомление запросит разрешение Notification Center; helper — одобрение в
  System Settings. Оба шага проведены через онбординг.

## 16. Будущее (вне текущего скоупа, отдельное ТЗ)

Автопополнение списка запрещённых: разбор `littlesnitch log-traffic` (root) →
гео-классификация направлений (GeoLite2-Country) → отчёт «эти приложения ходят на
зарубежные адреса напрямую и не в списке» → подтверждение пользователем → пополнение.
Возможный носитель — генерируемая `.lsrules`-подписка отдельной rule group (проверить,
принимает ли LS подписку на локальный файл). Автоматически в блок не добавлять — первым
кандидатом окажется системный процесс Apple.
