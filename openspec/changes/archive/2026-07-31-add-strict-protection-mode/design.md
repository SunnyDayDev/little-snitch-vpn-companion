# design — строгий режим защиты

## Context

Мотивация — в proposal.md. Технически существенное текущее состояние:

- Вся политика «состояние → целевые группы» сосредоточена в чистой доменной `LeakPolicy.targetEnabledGroups` (`Domain/LeakPolicy.swift`); для Offline/Paused она возвращает `nil` («не трогать»).
- `StateMachine` чистая и синхронная, события подаёт актор `MonitoringCoordinator`; настройки координатор читает лениво через `settingsProvider` при каждом обращении.
- `NetworkPathInfo.isSatisfied` уже приходит от `SystemPathMonitor`, но координатор его игнорирует — любое событие пути превращается в пробу (вердикт Offline появляется только после таймаута пробы).
- `probeGeneration` защищает от гонки «проба против пробы», но не «проба против пропажи сети».
- Обработчиков завершения приложения нет вовсе (нет `NSApplicationDelegate`); `coordinator.pause()` сбрасывает `isActive` **до** каких-либо reconcile, и `reconcile()` гейтится на `isActive`.
- Helper — stateless LaunchDaemon (SMAppService, on-demand по MachServices, живёт после первого запуска в `dispatchMain()`), три XPC-операции, без обработчиков invalidation входящих соединений, ничего не персистит. Root-демон не может читать user defaults приложения.
- Группы Little Snitch персистятся самим LS и применяются его фильтром с раннего этапа загрузки ОС — «закрыто на момент выключения» само по себе означает «закрыто на следующей загрузке».

Ограничение совместимости: при `protectionMode=reactive` (дефолт) поведение приложения и helper должно остаться байт-в-байт текущим.

## Goals / Non-Goals

**Goals:**

- Инвариант строгого режима «группы выключены ⇔ последний вердикт Protected и мониторинг активен» с четырьмя эшелонами гарантий: (1) штатный выход, (2) крэш — dead-man's switch helper, (3) выключение/перезагрузка — персистентность LS, (4) загрузка ОС — RunAtLoad-закрытие.
- Режим — параметр политики, а не вторая стейт-машина: минимальный диф в Domain.
- Немедленность закрытия: пропажа сети и смена сети закрывают до debounce, проб и вердиктов.

**Non-Goals:**

- Никаких escape hatch («Открыть на N минут») — ручной выход только средствами Little Snitch.
- Не переделываем детекцию (маяки, растяжка, РУ-маяк) — меняется только реакция на её вердикты.
- Не покрываем сценарий «helper тоже умер вместе с приложением» глубже RunAtLoad (kernel panic во время Protected закрывается только на следующей загрузке).
- Уведомления: новых категорий нет; переходы в/из Checking не уведомляются (шум при каждой смене сети).

## Decisions

### D1. Режим — параметр `LeakPolicy`, стейт-машина остаётся почти слепой к режиму

`ProtectionMode: String, Codable { case reactive, strict }` живёт в Domain. `LeakPolicy.targetEnabledGroups(for:mode:)`: reactive — как сейчас; strict — `state == .protected ? [] : managedGroups`. `ApplyPolicy.run` получает режим из настроек и передаёт в политику.

`StateMachine.handle(event, mode:)` получает режим аргументом от координатора (который читает его из live-настроек в момент события). Альтернативы: хранить режим полем машины и обновлять событием `.modeChanged` (отклонено — устаревшая копия настроек, лишняя синхронизация); ветвить в координаторе (отклонено — политика утекает из Domain, таблица §5 перестаёт быть проверяемой юнит-тестами машины).

Режимозависимых строк в таблице немного: `.started`, `.pathShifted`/`.pathChanged`, `.pathDown` (новые события), `.tripwireBroken`, `.userPaused`, `.userResumed`, вердикт `offline`. Остальные строки идентичны в обоих режимах. Проверки из устойчивого Protected (`.pathShifted`, `.tripwireBroken`) — мягкие: события эти часты, вердикт может протухнуть сразу после проверки и без них, а каждое превентивное закрытие — потерянные запросы; закрытие держится только для уже закрытых состояний (Offline/Checking → Checking).

### D2. Новое состояние `EgressState.checking`, вход только в строгом режиме

Полноценный кейс enum, а не UI-производная: Checking в строгом режиме — регулярно видимый этап (каждое пробуждение Mac), он обязан честно отражаться в журнале переходов, иконке и снапшоте. В реактивном режиме машина в него не входит (поведение дефолта не меняется). Альтернатива «вычислять в UI из offline + path.isSatisfied» отклонена: журнал и иконка врали бы, а семантика offline («сети нет») размылась.

`LeakPolicy`: reactive → checking не возникает, но на всякий случай маппится как offline (`nil`); strict → managedGroups.

### D3. Событие `pathDown` и инвалидация проб в полёте

Координатор начинает различать `info.isSatisfied`:

- Любое событие пути — **инкремент `probeGeneration`**: вердикт пробы, запущенной до события, описывает прошлую сеть и отбрасывается (иначе поздний protected открыл бы группы после закрытия или на непроверенной сети).
- `false` → событие `.pathDown`: немедленно (без debounce) `state = .offline`; в строгом режиме эффект `reconcile(.offline)` — закрытие. Действует в обоих режимах (в реактивном reconcile — no-op при `nil`-цели).
- `true` → `.pathShifted` немедленно (в строгом из Offline/Checking — `reconcile(.checking)`, удержание закрытого; из Protected — мягкая проверка без закрытия), затем после debounce `.pathChanged` → `probeNow`.

Порядок в координаторе: закрывающий reconcile выполняется до запуска пробы (эффекты уже исполняются последовательно в `execute`).

### D4. Пауза, тумблер и завершение: «сначала закрыть, потом умереть»

- `pause()` в строгом режиме: выполнить закрывающий reconcile **до** `isActive = false` и остановки слоёв. Машина в строгом режиме на `.userPaused` эмитит `[.reconcile(.paused)]`; координатор исполняет эффекты до деактивации. Гейт `isActive` в `reconcile()` сохраняется для отложенных/устаревших эффектов — закрывающий вызов проходит раньше сброса флага, семантика гейта не ослабляется.
- Тумблер «Мониторинг» выключен → тот же путь `pause()`.
- Завершение приложения: добавляется `AppDelegate` (`@NSApplicationDelegateAdaptor`), `applicationShouldTerminate` возвращает `.terminateLater`, в `Task` выполняется закрывающий reconcile (в строгом режиме), затем `reply(toApplicationShouldTerminate: true)`. Таймаут на весь путь (8 с — холодный XPC-вызов стоит до 6 с; закрытие на выходе идёт без листинга, одним идемпотентным включением на группу), чтобы зависший helper не блокировал выход навсегда — страховкой остаётся dead-man's switch.
- `resume()` в строгом режиме: `.userResumed` → `state = .checking`, группы уже закрыты (пауза закрыла), немедленная проба; открытие только по вердикту protected.

### D5. Helper: presence-соединение + персистентный failsafe-конфиг

- **Новая XPC-операция** `setFailsafe(config)`: `{ strictActive: Bool, groups: [String], supervisionTimeoutSeconds: Double }`. Приложение шлёт её при: включении/выключении строгого режима, изменении `leakGroups`, изменении `observeOnly` (observeOnly → `strictActive = false`), старте приложения (синхронизация). Контракт остаётся перечислимым (валидация клиента без изменений).
- **Персист**: helper пишет конфиг в `/Library/Application Support/dev.sunnyday.lsvpncompanion.helper/failsafe.json` (0644, владелец root). Читает при старте. User defaults приложения не трогаются.
- **Supervision (dead-man's switch)**: в listener-делегате helper вешает `invalidationHandler` на каждое принятое соединение и ведёт счётчик живых. Приложение в строгом режиме держит выделенное постоянное «presence»-соединение (не ленивое gateway-соединение), переустанавливаемое немедленно из invalidation-обработчика на стороне приложения. Helper: счётчик упал до нуля при `strictActive` → таймер `supervisionTimeoutSeconds` (дефолт 15 с) → по срабатыванию `littlesnitch rulegroup -e` для каждой группы конфига. Новое соединение отменяет таймер. Ложные срабатывания при переустановке helper исключаются порядком операций: приложение перед деregистрацией шлёт `strictActive=false`-конфиг (а после установки — заново `true`).
- **RunAtLoad**: в plist добавлен `RunAtLoad=true`; `main.swift` при старте читает конфиг и при `strictActive` включает группы с retry/backoff (2 с → 60 с, предел 10 мин). Гейт по uptime (< 5 мин, `BootClosePolicy`): перезапуск демона посреди сессии не закрывает поверх живого приложения. **Спайк 5.1 выполнен (2026-07-31)**: демон стартует при uptime ~40 с, UX одобрения не деградирует, CLI отвечает с первой попытки (~1 с); итог закрытия пишется в os_log и `boot-probe.log`.

Альтернатива «heartbeat-пинги вместо invalidation» отклонена: XPC invalidation — событийный, надёжный и бесплатный; пинги добавили бы таймеры с обеих сторон и те же ложные срабатывания.

### D6. Переключение режима на лету

`AppModel.update()` при смене `protectionMode`: журнал → `setFailsafe` в helper → немедленный reconcile переходной политикой: **reactive→strict** — закрыть, если вердикт не Protected (обычный strict-reconcile текущего состояния); **strict→reactive** — открыть, если вердикт не Leak. Второе не выражается реактивной политикой (она для Offline/Paused/Checking возвращает `nil`), поэтому в `ApplyPolicy` появляется явная операция «привести к цели» с целью, вычисленной для перехода (`state == .leak ? managedGroups : []`), применяемая один раз в момент переключения. Также при strict→reactive из Checking состояние машины нормализуется в Offline/по следующей пробе.

### D7. Эскалация и observeOnly

Условие эскалации Wi-Fi off **не расширяется**: только «вердикт Leak + helper недоступен» (в обоих режимах). Провал закрывающего reconcile при Offline/Checking — уведомление об ошибке + `needsReconcile`-повтор (механизм уже есть), без эскалации: там нет утечки, а Wi-Fi off при captive portal враждебен.

`observeOnly` побеждает всё: ApplyPolicy уже пропускает изменения групп; дополнительно observeOnly инактивирует failsafe-конфиг helper. UI на вкладке «Общие» показывает подпись-предупреждение, когда включены одновременно observeOnly и строгий режим.

### D8. Тесты

- `TestData.settings(mode:)`; существующие fail-open тесты фиксируются как ветка `.reactive`, зеркальная матрица для `.strict` (по режимозависимым строкам таблицы).
- Новый фейк «подвешиваемая проба» (continuation в `FakeBeacon`) для гонки «проба в полёте vs `pathDown`».
- Helper-логика supervision выносится в тестируемый тип (счётчик/таймер поверх абстракции часов) — сам XPC не юнит-тестится.
- RunAtLoad и поведение на живой загрузке — ручной приёмочный сценарий (§14), не юнит.

## Risks / Trade-offs

- [RunAtLoad в plist может конфликтовать с UX одобрения SMAppService или CLI недоступен на раннем этапе загрузки] → отдельный спайк на живой машине до реализации эшелона 4; фолбэк — выпустить без RunAtLoad: эшелоны 1–3 закрывают всё, кроме «power loss/паника при открытых группах», риск документируется в §15.
- [Ложное срабатывание dead-man's switch (сон/пробуждение, переустановка helper)] → presence-соединение переустанавливается из invalidation-обработчика немедленно; таймаут 15 с ≫ времени реконнекта; порядок «сначала strictActive=false, потом переустановка»; сон машины гасит и сеть — закрытие после пробуждения корректно по инварианту.
- [Churn групп LS в строгом режиме (каждая смена сети — закрыть/открыть)] → reconcile дифф-ориентирован (no-op, если фактическое состояние уже целевое); частота CLI-вызовов ограничена частотой смен сети; шум журнала принят осознанно.
- [Пользователь запер сам себя (браузер/VPN-клиент в группе, строгий режим, captive portal)] → предупреждение в онбординге и на вкладке «Группы»; ручной выход средствами LS задокументирован в §15; эскалации при Offline/Checking нет.
- [Устаревший helper без `setFailsafe` после обновления приложения] → существующий механизм отпечатка версии: приложение обнаруживает несовпадение и ведёт пользователя переустановить helper (как сейчас); строгий режим до переустановки работает эшелоном 1 (закрытие при выходе) с предупреждением в UI.
- [Зависший helper блокирует выход приложения] → таймаут в `applicationShouldTerminate` (~3 с) + dead-man's switch как страховка.

## Migration Plan

1. Дефолт `reactive`, ключа нет у существующих пользователей → поведение не меняется; helper-протокол расширяется аддитивно.
2. Порядок выката внутри изменения: Domain/политика → координатор → UI → helper-failsafe → RunAtLoad (после спайка). Строгий режим можно включать руками уже после первого этапа (эшелон 1 без helper-страховки).
3. Откат: выключить строгий режим (UI или `defaults write … protectionMode reactive`) → немедленный открывающий reconcile; helper-конфиг инактивируется.

## Open Questions

- Дефолт `supervisionTimeoutSeconds` (15 с — рабочая гипотеза; уточним по логам presence-реконнектов на живой машине).
- Точный SF Symbol для Checking (кандидаты: `shield` + `clock`, `arrow.triangle.2.circlepath` поверх щита) — решится в макетах.
- Результаты RunAtLoad-спайка могут сузить эшелон 4 (например, только KeepAlive-вариант) — фолбэк описан в Risks.
