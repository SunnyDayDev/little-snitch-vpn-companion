# Поддержка macOS 15 (Sequoia)

## Why

Приложение нельзя ни собрать, ни запустить на macOS 15: deployment target выставлен `26.0`, хотя ни одного API новее macOS 15 в коде нет — порог был взят по машине разработки, а не по фактическим требованиям. Из-за него отсекаются машины на Sequoia (в том числе 15.7), где Little Snitch 6 работает и сценарий «закрыть трафик при пропаже VPN» нужен ровно так же.

Проверено на месте (Xcode 26.6, SDK 26.5): Debug и Release собираются без единой диагностики availability и при пороге 15.7, и при заведомо более строгом 15.0; все 187 тестов проходят; `minos` обоих бинарей и `LSMinimumSystemVersion` равны выставленному порогу. Кода, требующего macOS 26, в проекте нет.

## What Changes

- Минимальная поддерживаемая версия macOS — **15.7** вместо 26.0 (deployment target в `project.yml`, оба места: `options.deploymentTarget` и `settings.base`). Порог равен версии, которая реально проверяется: сборочная машина — 15.7.8, образ CI — 15.7.7.
- CI получает **второй job на `macos-15`** (образ GitHub — macOS 15.7 с установленными Xcode 26.0.1–26.3): совместимость проверяется автоматически на обеих границах поддерживаемого диапазона, а не обнаруживается на чужой машине. Имя существующего job — «Тесты (macOS 26)» — не меняется: на него настроена защита ветки.
- Требования к ОС в документах расходятся на два разных: **для запуска** — macOS 15.7+; **для сборки** — macOS 15.6+ с Xcode 26.0–26.3 либо macOS 26.2+ с любым Xcode 26.x (Xcode 26.4 и новее на Sequoia не ставятся).
- Набор архитектур (`arm64` + `x86_64`) фиксируется явно: целевая машина оказалась Intel, а Xcode 26 в App Store отдаётся сборкой под Apple Silicon — единственный путь туда — перенос готового бандла, и потеря x86_64-слайса проявилась бы не ошибкой сборки, а неработающим приложением.
- Логика, UI, helper, тесты — **без изменений**. Расширяется только множество ОС и машин, где приложение работает.

**Не-цели:** macOS 15.6 и ниже — код там работал бы (ни одного API новее 15.0 не используется), но проверить эти версии не на чем, а заявлять шире проверенного не хотим; снижение порога позже — одна строка. Также вне рамок: отдельная ветка UI под Sequoia, отказ от SDK 26 и Xcode 26 при сборке.

## Capabilities

### New Capabilities

- `platform-support`: минимальная поддерживаемая версия macOS как явное свойство продукта — порог запуска, запрет на использование API новее порога без явного `@available`-гейта, автоматическая проверка обеих границ диапазона в CI.

### Modified Capabilities

Нет. Ни один сценарий существующих capabilities не меняет поведения: подсказки по одобрению демона ведут через `SMAppService.openSystemSettingsLoginItems()` (API сам знает нужный раздел в каждой версии ОС), используемые SF Symbols (`checkmark`, `shield.fill`) существуют с давних версий, рантайм-ветвлений по версии ОС в коде нет.

## Impact

- **`project.yml`**: `options.deploymentTarget.macOS` и `settings.base.MACOSX_DEPLOYMENT_TARGET` → `15.7`.
- **`.github/workflows/ci.yml`**: добавляется job «Тесты (macOS 15)» на `runs-on: macos-15` с явным выбором Xcode 26.x (по умолчанию на образе — 16.4, то есть SDK 15 и другой компилятор: без выбора проверялась бы не та конфигурация, что у разработчика).
- **Защита ветки**: новый job нужно добавить в required checks — это действие в настройках репозитория, вне кода; отмечается в `CONTRIBUTING.md`.
- **Документы**: `README.md` («Что понадобится», раздел про подпись/сборку), `SPEC.md` (§1 «min macOS 26», §15 «Swift 6 / SwiftUI, min macOS 26», §2 про машину разработки), `CONTRIBUTING.md` (упоминание обязательных проверок).
- **Код, тесты, спеки поведения**: не затрагиваются.
- **Ручная приёмка**: запуск на живой Sequoia — онбординг, регистрация демона через `SMAppService`, одобрение объекта входа, XPC-рукопожатие с проверкой сертификата, переключение rule groups. Компилятор эти сценарии не проверяет, а BTM и launchd на 15 и 26 — разные реализации.
