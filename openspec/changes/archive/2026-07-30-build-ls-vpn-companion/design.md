# Design: build-ls-vpn-companion

## Context

Мотивация — см. [proposal.md](proposal.md). Первоисточник всех требований — [SPEC.md](../../../SPEC.md) (согласовано 2026-07-29): все архитектурные развилки уже решены в §2 SPEC.md и **не перерешиваются**. Этот документ фиксирует, как решения ТЗ раскладываются на реализацию, и добавляет только то, чего в ТЗ нет.

Ключевые ограничения среды:

- Одна целевая машина: Apple Silicon, macOS 26.5.2; min macOS 26, Swift 6, только системные фреймворки.
- `littlesnitch` CLI работает только под root → обязателен привилегированный helper (LaunchDaemon).
- Подпись самоподписанным сертификатом, без нотарификации; App Sandbox выключен у обоих таргетов.
- Факты, помеченные в SPEC.md «проверено», сняты с целевой машины 2026-07-29 — им верить; структуру `export-model` и коды возврата `rulegroup` исполнитель проверяет на месте (§9 SPEC.md).

## Goals / Non-Goals

**Goals:**

- Clean Architecture + DDD: зависимости только внутрь, Domain — чистый Swift без Apple-фреймворков, полностью покрыт unit-тестами (state machine пишется первой, через TDD).
- Все side-effects — за портами (протоколами), чтобы Application-слой тестировался на фейках.
- Дизайн-система из `design/app.pen` переносится 1:1 в SwiftUI как отдельный модуль (имена компонентов сохраняются).
- Идемпотентность всех действий и reconcile как единственный способ применения политики.

**Non-Goals:**

- Собственное NE-расширение (content filter) — LS закрывает потребность (решение №14).
- Мониторинг каждого потока — меряется только путь маяка; частичная поломка сплита вне скоупа (§15 SPEC.md).
- Автопополнение списка запрещённых приложений (`log-traffic` + гео-классификация) — будущее, отдельное ТЗ (§16 SPEC.md).
- Поддержка других машин/версий macOS, нотарификация, локализации кроме русской.

## Decisions

### D1. Слои и структура таргетов

Структура — §10.3 SPEC.md: `App/` (Presentation + DesignSystem), `Application/`, `Domain/`, `Infrastructure/`, `Helper/`, `Tests/DomainTests/`, `Tests/ApplicationTests/`. Xcode-проект с двумя продуктовыми таргетами (app + helper); слои Domain/Application/Infrastructure — фреймворки или просто группы с жёсткой дисциплиной импортов (решается при создании скелета; критерий — Domain не импортирует ничего, кроме стандартной библиотеки Swift).

- **Domain**: `EgressState`, `ProbeResult`, `ProbeTrigger`, `LeakPolicy`, `RuleGroup`, `RuleGroupMapping`, `StateMachine` (таблица §5 SPEC.md), `JournalEvent`.
- **Application**: use cases `EvaluateProbe`, `ApplyPolicy` (reconcile), `SyncRuleGroups`, `PauseMonitoring`, `ResumeMonitoring`, `RunProbeNow`, `HandleHelperFailure`. Порты: `BeaconProbing`, `DirectIPProbing`, `TripwireMonitoring`, `PathMonitoring`, `RuleGroupGateway`, `WifiPowerGateway`, `NotificationPresenting`, `JournalStore`, `SettingsStore`, `Clock`.
- **Infrastructure**: `CloudflareBeaconProber` (URLSession ephemeral), `RuBeaconProber`, `TripwireConnection` (Network.framework), `SystemPathMonitor` (NWPathMonitor), `HelperRuleGroupGateway` (XPC-клиент), `NetworksetupWifiGateway`, `UserNotificationsPresenter`, `FileJournalStore` (JSONL, ротация 7 дней), `DefaultsSettingsStore`.
- **Presentation**: SwiftUI, MVVM поверх use cases; `MenuBarExtra` (window-стиль), окна Настройки/Журнал/Онбординг.

*Почему*: прямое следование §10 SPEC.md; порт `Clock` делает тестируемыми все временные аспекты (heartbeat, debounce, подтверждение утечки, backoff).

### D2. Конкурентная модель детектора

Детектор — актор (Swift 6 strict concurrency): события от трёх слоёв (растяжка, path monitor, таймер плановых проб) сериализуются в одну очередь обработки, там же живут debounce (~300 мс) и логика двойного подтверждения (2 пробы / 2.5 с). Это исключает гонки «событие пути пришло во время подтверждающей пробы» по построению.

*Альтернатива*: DispatchQueue + локи — отвергнуто: Swift 6 даёт compile-time-гарантии изоляции, а Domain остаётся синхронным и тривиально тестируемым (актор — на уровне Application/Infrastructure, не в Domain).

### D3. Растяжка: ручной HTTP поверх NWConnection

Растяжка — `NWConnection` (TLS, порт 443) с рукописным минимальным `GET /cdn-cgi/trace HTTP/1.1` + `Connection: keep-alive` раз в 15 с и дедлайном чтения 5 с. URLSession для растяжки не годится: он прячет жизненный цикл соединения (пулинг, прозрачные реконнекты), а нам нужен именно сырой сигнал обрыва TCP/TLS.

Парсинг ответа heartbeat — минимальный (достаточно валидной статусной строки HTTP; тело можно не разбирать — классификация состояния делается только свежими пробами). Обрыв/дедлайн → сигнал в детектор → немедленная свежая проба; переустановка с экспоненциальным backoff 2→60 с.

### D4. Пробы: два независимых прибора

- **Foreign-проба** (`CloudflareBeaconProber`): каждая проба — новый `URLSession` с `.ephemeral`-конфигурацией (без кэша, без переиспользования соединений), таймаут 6 с; сначала основной маяк, при сбое — резервный по IP. Парсер `key=value` терпим к лишним строкам; ответ без `ip=` → offline.
- **РУ-проба** (`RuBeaconProber`): тоже ephemeral, таймаут 6 с; для `2ip.ru` — явный curl-подобный User-Agent; тело валидируется как IP (v4/v6) стандартным парсером адресов, иначе отбрасывается.

Результат РУ-пробы не является событием состояния — он только обновляет динамическую запись `FORBIDDEN_EGRESS` (с guard: если ответ равен текущему protected-egress — не добавлять, предупреждение в журнал) и триггерит внеочередную foreign-пробу.

### D5. Reconcile как единственный канал изменения групп

`ApplyPolicy` всегда работает по схеме: получить фактический список групп (`listRuleGroups` через helper) → вычислить целевой набор для текущего состояния (`LeakPolicy`) → выполнить только недостающие `setRuleGroup`-операции. Никакого состояния «мы включали» в приложении нет. Ошибка любой операции: состояние детектора не меняется, флаг «helper недоступен», журнал + уведомление, при Leak — эскалация.

*Почему*: LS — внешняя система, группы может переключить сам пользователь; единственная надёжная стратегия — сверка с фактом (решение §5 SPEC.md «Reconcile, а не история»).

### D6. Helper: SMAppService + XPC, безопасность

- Регистрация: `SMAppService.daemon(plistName:)`, plist в `Contents/Library/LaunchDaemons/dev.sunnyday.lsvpncompanion.helper.plist` с `BundleProgram` и `MachServices = dev.sunnyday.lsvpncompanion.helper`.
- XPC-контракт — ровно три метода (`version`, `listRuleGroups`, `setRuleGroup`) из §10.2 SPEC.md; произвольные команды не проходят по построению.
- Валидация клиента: audit token соединения → `SecCodeCopyGuestWithAttributes` → проверка code-signing requirement (тот же сертификат + bundle id `dev.sunnyday.lsvpncompanion`). Соединения, не прошедшие проверку, инвалидируются до обработки сообщений.
- Вызов CLI: `Process` с абсолютным путём `/Applications/Little Snitch.app/Contents/Components/littlesnitch`, таймаут 3 с, захват stdout/stderr. `export-model` парсится выборочно (только имена групп + enabled) стриминговым/толерантным декодером — модель может быть большой, формат не документирован; неудача парсинга — внятная ошибка в reply, не крэш.
- Версионирование: `version()` сверяется приложением при старте; несовпадение → предложение переустановить helper (кнопка в настройках).

### D7. Эскалация

`NetworksetupWifiGateway` (в приложении, root не нужен): устройство Wi-Fi определяется парсингом `networksetup -listallhardwareports` (искать порт «Wi-Fi»; на целевой машине это `en0`, но не хардкодить), выключение — `networksetup -setairportpower <dev> off`. Вызывается только из `HandleHelperFailure` при подтверждённом Leak, `escalationEnabled=true` и `observeOnly=false`.

### D8. Дизайн-система как модуль

Отдельный SwiftUI-модуль `DesignSystem`: токены (§8.1–8.3) как семантические `Color`/константы с light/dark вариантами, атомы (§8.4) и молекулы (§8.5) как переиспользуемые View с именами из макетов `design/app.pen`. Правило: экранные вью не содержат хардкод-цветов/размеров — только токены и компоненты. Где уместно, токены мапятся на системные эквиваленты (`.primary`, `.secondary`, `Color.accentColor`), сохраняя соответствие таблице §8.1. При противоречии макетов и текста ТЗ — текст главнее (§17 SPEC.md).

### D9. Debug-режим для приёмки

Тест-план §14 SPEC.md требует скрытых debug-рычагов: «игнорировать warp=on» (сценарий 2–3) и подмена ответа маяка (сценарии 13–14). Реализация: скрытые defaults-ключи (например, `debugIgnoreWarp`, `debugFakeEgressIP`), читаемые пробером; в UI не отображаются, включаются через `defaults write`. Это дешёвле отдельного debug-меню и не светится в продуктовом UI.

### D10. Наблюдаемость

`os.Logger` (subsystem = bundle id, категории по слоям: detector, policy, helper, ui) + доменный журнал (ФТ-6) через `FileJournalStore`. Журнал — источник для окна UI и экспорта; os_log — для отладки через Console.app. Оба пишутся из одного потока событий Application-слоя, чтобы не расходились.

## Risks / Trade-offs

- **[Окно обнаружения до ~60 с]** в случае «старый поток жив, новые текут мимо» → принято в ТЗ (§15); митигируется тремя слоями детектора, типовые отвалы ловятся за секунды.
- **[Формат `export-model` не документирован и может меняться]** → выборочный толерантный парсинг, внятная ошибка вместо падения, версии helper и CLI в UI; проверка структуры на месте при реализации (§9 SPEC.md).
- **[Сторонние РУ-маяки неофициальные]** → два конфигурируемых endpoint'а, валидация ответа как IP, сбой некритичен (запись просто устаревает).
- **[Cloudflare-маяки недоступны]** → Offline — безопасное состояние (группы не трогаются); свой маяк решено не поднимать.
- **[Самоподписанная подпись]** → валидна только локально; при переносе на другую машину пересоздать сертификат и переподписать (машина одна — приемлемо). Hardened Runtime включить, если не конфликтует с локальной подписью.
- **[XPC-валидация по self-signed сертификату]** → requirement строится по конкретному листовому сертификату (anchor = designated requirement с hash сертификата), а не по Apple-цепочке; проверить работоспособность `SecCodeCheckValidity` с self-signed при реализации helper — если строгий requirement не собирается, зафиксировать fallback (сверка team/bundle id + путь бандла) с явным комментарием о снижении гарантии.
- **[Sleep/wake и смена сети]** → растяжка обязана переустановиться (backoff сбрасывается по событию пути), path monitor триггерит пробу; приёмочный сценарий 10 (§14) проверяет это явно.
- **[Эскалация выключает Wi-Fi, но не Ethernet]** → принято: ТЗ определяет эскалацию только для Wi-Fi (ФТ-9); машина — MacBook, типовой сценарий — беспроводная сеть.

## Migration Plan

Проект новый — миграции нет. Порядок ввода в строй (§12 SPEC.md): после приёмки — сутки обкатки в `observeOnly`, затем боевой режим. Откат — выключить мониторинг тумблером или удалить приложение + `SMAppService.unregister` для helper; группы LS при этом остаются как есть (пользователь выключает их в LS вручную при необходимости).

## Open Questions

Вопросов, меняющих спеки/подход/разбиение задач, нет — развилки решены в §2 SPEC.md. На месте (во время реализации, без влияния на план) уточняются:

- точная структура JSON `export-model` и коды возврата `rulegroup` (повторное включение включённой группы; несуществующее имя);
- совместимость строгого code-signing requirement с self-signed сертификатом (см. риск выше);
- работает ли Hardened Runtime с локальной подписью без нотарификации.
