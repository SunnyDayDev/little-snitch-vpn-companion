# Единый жизненный цикл helper: ожидание launchd, кнопка по состоянию, удаление

## Why

После замены бандла (`Scripts/install.sh` 2026-09-09, issue #22) от запуска приложения до рабочего helper прошло около двух минут, и всё это время кнопка «Переустановить…» отвечала ошибкой «helper недоступен: … No such process». Журнал приложения и лог запусков демона (`boot-probe.log`) показывают, что новый helper стартовал ровно один раз, через 30 с после последнего `register()`, а всё окно до этого в системе не было ни одного процесса helper: каждый новый цикл `unregister → register` не «перезапускал» демон, а сбрасывал ожидание Background Task Management с нуля.

Причины в коде: замена бандла даёт `SMAppService.status == .notRegistered` при живом старом демоне, и авто-восстановление регистрирует поверх него, не дожидаясь ответа; бюджет ожидания после регистрации (пять попыток по две секунды) короче наблюдаемой задержки BTM; каждое нажатие кнопки запускает отдельную задачу, и несколько переустановок идут одновременно, переключаясь на каждом `await`; проверка версии требует статуса `enabled`, которого после замены бандла нет. Логика живёт в `AppModel` без единого теста, и ни одно из этих поведений (авто-восстановление, вотчдог, проверка версии, тихий демон, кнопка) не описано в спеках.

## What Changes

- **Жизненный цикл helper становится одним use case Application-слоя** с явным состоянием: не зарегистрирован, не найден в бандле, ждёт одобрения, в работе (установка / переустановка / удаление), подключён, устарел, молчит. Все пути к регистрации (онбординг, авто-восстановление, проверка версии, кнопка, вотчдог) проходят через него; повторные запросы во время операции присоединяются к текущей, а не начинают новую.
- **Ожидание после регистрации** получает бюджет порядка минуты с нарастающим интервалом опроса; пока идёт ожидание, приложение показывает «ждём launchd… N с», а не ошибку. Только по исчерпании бюджета делается один полный цикл `unregister → register`, после него ещё одно ожидание, и лишь затем состояние «зарегистрирован, но не отвечает». Авто-восстановление потерянной регистрации ждёт ответа так же, как обновление.
- **Кнопка в строке «Привилегированный helper» выводится из состояния**: «Установить…» когда не зарегистрирован, «Переустановить…» когда версия отличается или демон молчит, «Удалить…» когда подключён актуальный helper или ждёт одобрения; во время операции кнопка неактивна и называет операцию. Ссылка «Открыть Системные настройки…» живёт в строке статуса, а не в кнопке.
- **Удаление helper** по кнопке: снятие регистрации с предварительным сбросом failsafe-конфигурации; факт удаления запоминается, чтобы авто-восстановление не вернуло демон при следующем запуске. Без предупреждений и подтверждений в любом режиме защиты.
- **Шаг 1 онбординга** выводится из того же состояния: неактивная кнопка «Устанавливаем…» во время регистрации, строка статуса со ссылкой при ожидании одобрения, закрытый шаг при подключённом helper.
- **Журнал**: переходы состояния helper пишутся по одному разу, ошибки шлюза во время ожидания не повторяются каждые несколько секунд.
- **Дизайн-система**: неактивные варианты первичной и вторичной кнопок, ссылка в подписи строки настройки, строка статуса в карточке-шаге. Макеты состояний (light и dark) уже добавлены в `design/app.pen`: экран «Настройки — helper: состояния» и полоса «Онбординг — шаг 1: состояния».
- **Документация**: README (грабли «Пересборка helper», «Мелочи эксплуатации helper»), `SPEC.md` §7.2 (кнопка по состоянию).
- Не BREAKING: XPC-контракт и код `Helper/` не меняются, перерегистрация демона из-за этого изменения не требуется; новых пользовательских настроек нет.

## Capabilities

### New Capabilities

- `helper-lifecycle`: состояния привилегированного helper и переходы между ними; ожидание ответа после регистрации и эскалация к полному циклу; коалесцирование одновременных запросов; авто-восстановление потерянной регистрации и его отключение после удаления пользователем; проверка версии работающего демона; удаление; единое представление состояния (кнопка, строка статуса, ссылка) для настроек, онбординга и поповера; записи в журнал.

### Modified Capabilities

- `app-settings`: строка «Привилегированный helper» на вкладке «Общие» показывает кнопку и подпись по состоянию helper со ссылкой на Системные настройки в подписи; строка про запрет CLI со стороны Little Snitch остаётся отдельной.
- `onboarding`: шаг 1 выводится из состояния helper: неактивная кнопка во время регистрации, строка статуса со ссылкой при ожидании одобрения, закрытый шаг при подключённом helper; сценарий «Установка helper из онбординга» уточняется.

## Impact

- `Application/HelperLifecycle.swift` (новый) — use case с состоянием, ожиданием, эскалацией и представлением; `Application/Ports.swift` — порт регистратора демона и порт факта «удалён пользователем».
- `Infrastructure/HelperInstaller.swift` — становится адаптером порта регистратора: статус, `register`, `unregister`, открытие Системных настроек, версия бандла; ожидания переезжают в use case.
- `App/AppModel.swift` — удаление собственных флагов и циклов ожидания (`restoreHelperIfLost`, `checkHelperVersion`, `updateHelperRegistration`, `waitForHelperToAnswer`, `recoverSilentHelperIfNeeded`), делегирование в use case; диагноз и вотчдог читают его состояние.
- `App/Screens/SettingsWindow.swift`, `App/Screens/OnboardingWindow.swift`, `App/Screens/MenuBarPopover.swift` — кнопка, подпись, ссылка и статус по состоянию.
- `App/DesignSystem/Atoms/DSButtons.swift`, `App/DesignSystem/Molecules/DSSettingRow.swift`, `App/DesignSystem/Molecules/DSStepCard.swift` — неактивные кнопки, ссылка в подписи, строка статуса.
- Тесты: `Tests/ApplicationTests/HelperLifecycleTests.swift` (новый) на фейках регистратора и шлюза с `ManualClock`; `Tests/ApplicationTests/Fakes.swift` — фейк регистратора, версия helper по сценарию.
- `README.md`, `SPEC.md` §7.2; `design/app.pen` (макеты уже нарисованы).
- Helper не пересобирается: отпечаток демона не меняется, установка обновления не требует перерегистрации.
