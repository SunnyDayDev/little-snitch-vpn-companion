# tasks — закрытие групп при уходе машины в сон

## 1. Domain: события питания в таблице переходов

- [x] 1.1 `StateMachine.Event`: кейсы `systemWillSleep` и `systemDidWake`. Обработка `systemWillSleep`: в реактивном режиме — пустой список эффектов; в строгом — из не-`Paused` состояний переход в `.checking` с `[.reconcile(.checking)]`, из `Paused` — состояние не меняется, эффект `[.reconcile(.paused)]` (идемпотентная страховка). Взвести `needsReconcile`, чтобы первый вердикт после пробуждения гарантированно сверился
- [x] 1.2 Обработка `systemDidWake`: из `Paused` — пустой список; иначе `[.probeNow(.power)]` в обоих режимах
- [x] 1.3 `ProbeTrigger` + кейс `power`
- [x] 1.4 Тесты `StateMachineTests` на каждую новую строку таблицы: засыпание из Protected/Leak/Offline/Checking в строгом (→ Checking + закрывающий reconcile), засыпание в реактивном (эффектов нет), засыпание на паузе (Paused сохраняется, reconcile есть только в строгом), пробуждение в обоих режимах, пробуждение на паузе (эффектов нет)
- [x] 1.5 Тест на застревание закрытым: `systemWillSleep` из Protected → `systemDidWake` → проба `protected` → обязан прийти `reconcile(.protected)` (регрессия на `needsReconcile`)

## 2. Application: порт и координатор

- [x] 2.1 Порт `PowerMonitoring` в `Ports.swift` по образцу `PathMonitoring`: `start(onWillSleep:onDidWake:)` / `stop()`. Обработчик засыпания обязан быть «ожидаемым» — координатор должен уметь сообщить инфраструктуре, что закрытие завершено (через async-обработчик, чей возврат и есть сигнал «можно спать»)
- [x] 2.2 `FakePowerMonitor` в `Tests/ApplicationTests/Fakes.swift`: ручное порождение засыпания и пробуждения, запись факта завершения обработчика
- [x] 2.3 `MonitoringCoordinator.handleSystemWillSleep()`: инкремент `probeGeneration`; `guard !isTerminating`; журнал факта с триггером `power`; в строгом режиме — `applyPolicy.forceEnable(groups:settings:)` **напрямую**, минуя гейт `guard isActive` в `reconcile()` (на паузе `isActive == false`); диспатч событию машины; при провале — журнал предупреждения и `dispatch(.helperFailed)`
- [x] 2.4 `MonitoringCoordinator.handleSystemDidWake()`: журнал факта с триггером `power`; `guard isActive` и диспатч `systemDidWake`
- [x] 2.5 Подписка на порт поднимается в `start()` и снимается в `stop()`/`prepareForTermination()` — **не** в `startDetectorLayers`/`stopDetectorLayers`, иначе пауза выключала бы эшелон (Решение 5 в design.md)
- [x] 2.6 `ApplyPolicy.forceEnable` при `observeOnly` пишет в журнал «строгий режим: закрыл бы группы — наблюдение, не тронуты», как это делает `run(target:)` (сейчас молча возвращает `skippedObserveOnly`)
- [x] 2.7 Тесты координатора: закрытие при засыпании в строгом; группы не тронуты в реактивном; закрытие идемпотентно выполняется на паузе; `observeOnly` не трогает группы, но пишет журнал; провал закрытия взводит «helper недоступен» и Wi-Fi не выключается; пробуждение запускает пробу без события пути
- [x] 2.8 Тест гонки: подвешенная проба стартует до засыпания, засыпание закрывает группы, затем проба возвращает `protected` → вердикт отброшен, группы остались включены (использовать continuation-подвес `FakeBeacon`, как в тесте `pathDown`)

## 5. Живая приёмка

- [x] 5.1 Строгий режим, состояние Protected: `pmset sleepnow`, сон ≥5 мин, пробуждение. Ожидание: в журнале запись о засыпании с триггером «питание» и включение группы; группы включены на всё время сна; выключаются только после вердикта Protected после пробуждения
- [ ] 5.2 Реактивный режим, тот же сценарий. Ожидание: запись о засыпании есть, записей об изменении групп нет
- [x] 5.3 Замер задержки засыпания: `pmset -g log` после сна — строка `PM Client Acks: Delays to Sleep notifications` должна показывать задержку приложения в пределах бюджета (норма ~1 с), и отсутствие записи о неотвеченном уведомлении
- [ ] 5.4 Ночной прогон: утром снять `journal.jsonl` и `pmset -g log`, сверить, что каждому dark wake соответствует запись о пробуждении, а каждому последующему засыпанию — своя запись о закрытии

## 7. Липкий сон (по итогам живой приёмки 5.1, замер 2026-08-02 16:01–16:05)

- [x] 7.1 `StateMachine`: липкий флаг `isAsleep` (взводится `systemWillSleep`, снимается только `systemDidWake` — полным пробуждением); в строгом режиме вердикт `protected` при взведённом флаге не открывает (состояние остаётся `Checking`, `needsReconcile` взведён); закрывающие вердикты не подавляются. Тесты: protected в dark wake не открывает, после полного пробуждения открывает, Leak во сне закрывает, отменённое засыпание снимает флаг
- [x] 7.2 Тест координатора: start → сон → событие пути в dark wake с protected-вердиктом → группы остаются включены → полное пробуждение → проба открывает
- [x] 7.3 Спеки и SPEC.md: dark wake — не пробуждение, окно сна размечено парой «WillSleep → HasPoweredOn», внутри окна открытие запрещено; §14 п.23 дополнен; §15 — находка «возврат из dark wake в сон не сообщается»
- [x] 7.4 Переустановка и повторная живая приёмка: сон ≥5 мин с dark wake — группы не открываются в dark wake (нет «группа … выключена» между засыпанием и полным пробуждением)
