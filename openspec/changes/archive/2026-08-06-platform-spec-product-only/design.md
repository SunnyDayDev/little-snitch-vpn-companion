## Context

См. `proposal.md` — Why. Здесь только то, что нужно для решений: какой критерий отделяет продукт от процесса и что делать с пограничными формулировками, которые остаются в спеке.

Дельта — единственная в проекте правка спеки, не сопровождаемая изменением поведения. Ни одна строка кода не трогается, поэтому обычная проверка «работает или нет» здесь ничего не подтверждает: корректность изменения — в том, что после него спека продолжает удерживать все обещания продукта и не удерживает ничего сверх.

Спека `platform-support` — единственная из десяти живых, где вообще встречаются слова CI, Xcode и «мерж». Остальные девять уже соответствуют критерию; проверено grep'ом по `openspec/specs/`.

## Goals / Non-Goals

**Goals:**

- Зафиксировать критерий, по которому требование признаётся продуктовым, — чтобы спека не дрейфовала обратно при следующей смене тулчейна.
- Сохранить все продуктовые гарантии дословно: диапазон запуска, `minos`, `LSMinimumSystemVersion`, универсальный артефакт, запрет на API новее порога.
- Привести `README.md` в соответствие с фактом: сборка требует macOS 26.

**Non-Goals:**

- Проверять, что удаляемые требования выполняются, — они удаляются как неуместные в спеке, а не как нарушенные.
- Ревизовать остальные девять capabilities.
- Заводить отдельный документ «политика спек»: критерий фиксируется здесь и в тексте самой дельты.

## Decisions

### Решение 1: критерий — «переживёт ли требование замену инструмента»

Требование продуктовое, если оно остаётся верным при полной замене тулчейна, CI-провайдера и способа сборки. Требование процессное, если смена инструмента делает его ложным.

Проверка критерием по текущему содержимому спеки:

| Требование | Замена тулчейна ломает? | Вердикт |
|---|---|---|
| Запуск на 15.7+, `minos`, `LSMinimumSystemVersion` | нет | продукт, остаётся |
| Универсальный артефакт (`arm64` + `x86_64`) | нет | продукт, остаётся |
| Никаких API новее порога без `@available` | нет | продукт, остаётся |
| «Заявленная поддержка = проверенная» | нет | продукт, остаётся |
| Проверка обеих границ в CI | да — уже сломалась | процесс, удаляется |
| Список для сборки: версии macOS и Xcode | да — уже сломалась | процесс, удаляется |

Альтернатива — «спека описывает всё, что важно для проекта» — отвергнута: именно она привела к тому, что переход иконки на Icon Composer сделал спеку ложной, не изменив продукт.

### Решение 2: удаление через REMOVED + ADDED, а не MODIFIED

Требование «Раздельные требования к запуску и к сборке» теряет один из двух сценариев. `openspec validate` отвергает MODIFIED, где сценарий существующего требования пропал: MODIFIED заменяет блок целиком, и архивация иначе молча потеряла бы содержимое.

Поэтому старое требование удаляется с `Reason`/`Migration`, а его продуктовая половина добавляется как новое требование «Порог запуска не завышается требованиями к сборке» с новым, честным именем — старое имя обещало симметрию двух списков, которой больше нет.

Альтернатива — RENAMED с последующим MODIFIED — отвергнута: она прячет удаление сценария за переименованием, тогда как удаление здесь и есть суть правки.

### Решение 3: `Deployment target SHALL быть 15.7` остаётся в спеке

Формально это имя настройки сборки. Оставлено сознательно: это единственная запись порога, которую нельзя вывести из наблюдаемых свойств артефакта задом наперёд, и она не зависит ни от CI, ни от версии Xcode. Смена тулчейна её не ломает — критерий из решения 1 выполняется.

Альтернатива — оставить только `minos` и `LSMinimumSystemVersion` — отвергнута как чрезмерная: получилось бы требование к следствию без требования к причине.

### Решение 4: сценарий про availability остаётся, хотя упоминает сборку

Требование «Никаких API новее минимального порога» говорит, что нарушение проявляется диагностикой availability при сборке. Это не механика CI: диагностика следует из deployment target и возникает на любом хосте, любым Xcode 26.x. Требование описывает свойство исходников, а место обнаружения — его неотъемлемая часть, а не выбор инструмента.

### Решение 5: `Purpose` правится в основной спеке, а не дельтой

`Purpose` капабилити сейчас упоминает «автоматическую проверку обеих границ диапазона перед мержем». Дельта-файл существующей capability `Purpose` не переносит — он игнорируется при архивации. Поэтому правка `Purpose` идёт отдельной задачей прямо в `openspec/specs/platform-support/spec.md` и должна быть сделана в том же изменении, иначе в спеке останется ссылка на удалённое требование.

## Risks / Trade-offs

**Гарантия совместимости остаётся без нормативного гейта в спеке** → продуктовое требование «заявленная поддержка означает проверенную» сохраняется и продолжает запрещать заявлять непроверенное; фактический прогон тестов на macOS 15 сохраняется в `ci.yml` и обязателен для мержа по ruleset'у защиты `main`. Изменилось только то, где это записано, — риск в том, что джобу когда-нибудь снимут, не заметив нарушения продуктового требования.

**`Purpose` рассинхронизируется с требованиями** → закрывается решением 5: правка идёт в том же изменении, а не откладывается до архивации.

**Кто-то прочтёт удаление требования как отказ от поддержки macOS 15** → в `Reason` и `Migration` прямо сказано, что диапазон запуска не меняется и где живёт проверка; `README.md` продолжает заявлять 15.7–26.x.

**Регресс компиляции `App/` под тулчейном Sequoia больше не ловится** → принято осознанно: поставляемый артефакт всё равно собирается на macOS 26, а сценарий «контрибьютор собирает на Sequoia» невозможен независимо от CI. Риск ограничен неудобством контрибьютора, которого сейчас нет.

## Migration Plan

Изменение чисто документационное: правки в `openspec/` и `README.md`, ни одного файла с кодом. Откат — `git revert` одного коммита, никаких последствий для собранных артефактов и установленных копий.
