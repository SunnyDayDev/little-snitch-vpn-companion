# Спека платформы — только про продукт, не про процесс сборки

## Why

`platform-support` — единственная из десяти живых capabilities, где спека предписывает не свойства продукта, а способ его изготовления: что именно прогоняет CI, на каких образах, какой мажорной версией Xcode, и что разработчик собирает проект на минимальной поддерживаемой macOS. Такие требования краснеют при каждом изменении тулчейна, к поведению приложения отношения не имеющем.

Это уже произошло. Перевод иконки на Icon Composer (PR #14) сделал сборку app-таргета на macOS 15 невозможной: `actool` падает с `IBPlatformToolFailureException` («the tool closed the connection (AssetCatalogAgent-AssetRuntime)») при компиляции `App/AppIcon.icon`. Спека немедленно разошлась с `main` в трёх местах — при том, что ни одно свойство продукта не изменилось: приложение как работало на 15.7, так и работает.

Спека должна фиксировать, **чем является продукт**; чем именно эта гарантия обеспечивается — вопрос процесса, который обязан меняться без правки спек.

## What Changes

- **Требование «Проверка обеих границ диапазона в CI» удаляется целиком** — вместе со всей механикой: образы, мажорные и минорные версии Xcode, «сборку и тесты», обязательность проверок для мержа. Сам прогон тестов на macOS 15 в CI сохраняется как есть и продолжает работать — он просто перестаёт быть предметом спеки. Его место — `CONTRIBUTING.md` и `.github/workflows/ci.yml`, где он уже описан.
- **Требование «Раздельные требования к запуску и к сборке» заменяется** на «Порог запуска не завышается требованиями к сборке». Из него уходит предписание, что именно перечислять в списке для сборки (версии macOS и Xcode — свойства сборочного окружения), и сценарий «Сборка на минимальной macOS»: собрать приложение на macOS ниже 26 больше нельзя. Пользовательская половина сохраняется полностью — документация обязана показывать порог запуска, не завышенный требованиями сборочной машины.
- **Из требования «Минимальная поддерживаемая версия macOS» убирается процессная вставка** про то, что сборка ведётся против актуального SDK 26.x, а не против SDK минимальной версии.
- **Purpose capability переписывается**: из формулировки уходит «автоматическая проверка обеих границ диапазона перед мержем».
- **`README.md` исправляется**: раздел «Что понадобится» сейчас утверждает, что собирать можно на Sequoia с Xcode 26.0–26.3. После PR #14 это неверно — требуется macOS 26.

Сохраняются без изменений по существу: запуск на macOS 15.7+ и на 26.x, `minos 15.7` в обоих бинарях и `LSMinimumSystemVersion`, универсальный артефакт со слайсами `arm64` + `x86_64` и его нативная работа на Intel-машине с macOS 15.7.8, запрет на API новее минимального порога без `@available`-гейта, политика «заявленная поддержка означает проверенную поддержку».

**Не-цели:** возвращать возможность сборки на Sequoia — для этого пришлось бы держать `AppIcon.appiconset` параллельно с Icon Composer, а иконка уже принята в текущем виде; менять `ci.yml`, схемы сборки или deployment target; сужать или расширять поддерживаемый диапазон запуска; трогать остальные девять capabilities.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `platform-support`: удаляются требования «Проверка обеих границ диапазона в CI» и «Раздельные требования к запуску и к сборке»; взамен добавляется «Порог запуска не завышается требованиями к сборке» — продуктовая половина второго; из требования о минимальной версии уходит процессная деталь про SDK. Требования об артефакте (порог запуска, универсальность, запрет на новые API) остаются.

## Impact

- **`openspec/specs/platform-support/spec.md`** — приводится к дельте при архивации: минус одно требование, минус один сценарий, две правки формулировок (Purpose и требование о минимальной версии).
- **`README.md`** — раздел «Что понадобится», блок «Для сборки»: macOS 26+ вместо Sequoia с Xcode 26.0–26.3. Строка «Проверено» ниже тоже описывает сборку на образе macOS 15.7 — её нужно привести в соответствие.
- **`CONTRIBUTING.md`** — правки не требуются: обе проверки там уже описаны как процесс, и это остаётся их единственным нормативным домом.
- **`SPEC.md`** — правки не требуются: упоминание 15.7.8 в §1 описывает машины пользователя, а не требования к сборке.
- **Код, `project.yml`, `ci.yml`, тесты** — не затрагиваются. Поведение приложения не меняется ни на одной поддерживаемой версии macOS.
