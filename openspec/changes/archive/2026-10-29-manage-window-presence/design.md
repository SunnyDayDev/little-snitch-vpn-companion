# Управление жизненным циклом окон

## Context

Мотивация описана в [proposal.md](proposal.md). `LSVPNCompanionApp` объявляет три уникальные сцены `Window` и `MenuBarExtra` со стилем `.window`. В `MenuBarPopover` оба перехода вызывают `openWindow` и `model.activateApp()`, но не закрывают поповер. `project.yml` задаёт `LSUIElement: YES`; переключения политики активации нет. В README и текущей спеке закреплено постоянное отсутствие Dock — это правило намеренно заменяется.

Онбординг открывается из задачи `MenuBarLabel`, а завершение связано с `OnboardingWindow.onDisappear`. Существующие тестовые таргеты компилируют нижние слои напрямую и не включают `App/`. Дизайн нужен, чтобы определить общий учёт окон и порядок перехода между поповером и окном до реализации.

## Goals / Non-Goals

**Цели:** единый владелец присутствия в Dock в слое `App/`, явный учёт основных окон и проверяемый порядок действий. Мониторинг не зависит от жизненного цикла окон.

**Вне задачи:** перенос окон на полностью ручное создание AppKit, новые настройки Dock, изменение содержимого окон и действий мониторинга, изменение политики завершения процесса. Закреплённые пользователем иконки и системный список недавних приложений не удаляются: приложение управляет своим активным присутствием, а не настройками Dock.

## Decisions

### 1. Один координатор окон в слое App

Добавить `@MainActor`-координатор, принадлежащий корню приложения. Он знает роли `settings`, `journal`, `onboarding`, зарегистрированные экземпляры окон и их состояние «открыто / закрыто». SwiftUI-мост получает конкретный `NSWindow` из представления каждой основной сцены и передаёт его координатору. Поповер получает отдельную ссылку только для закрытия и не регистрируется как основное окно.

Учёт должен переживать повторное использование SwiftUI ранее закрытого экземпляра окна: повторный показ вновь помечает его открытым. Закрытие снимает отметку, повторное событие регистрации или закрытия идемпотентно. Сворачивание, скрытие и потеря фокуса отметку не снимают. Наблюдатели освобождаются при смене экземпляра; отложенное событие старого окна не удаляет новый экземпляр той же роли.

Альтернатива — проверять `NSApp.windows` или `isVisible` всех окон. Она смешивает поповер, панели и основные окна, а свёрнутое или скрытое окно ошибочно принимает за закрытое. Пара `onAppear` / `onDisappear` также не должна быть единственным источником истины о закрытии.

### 2. Политика активации следует наличию открытых основных окон

Сохранить `LSUIElement` для фонового старта. При открытии первого основного окна запрашивать `.regular`, после закрытия последнего — `.accessory`. На промежуточных событиях без смены требуемого режима повторный запрос не нужен. Проверять результат смены политики; не считать неуспешный запрос применённым и не скрывать само окно из-за ошибки.

Выбор основан на [документации Apple о политике активации](https://developer.apple.com/documentation/appkit/nsapplication/activationpolicy-swift.enum): `.regular` предоставляет присутствие в Dock, `.accessory` позволяет показывать окна без Dock. Это также меняет системное представление приложения в переключателе приложений; отдельная политика для него не вводится.

Постоянное удаление `LSUIElement` не подходит: иконка была бы видна и без окон. Смена режима при потере фокуса не подходит: пользователь должен возвращаться через Dock. `applicationShouldTerminateAfterLastWindowClosed` должен явно сохранять процесс, а существующий путь `applicationShouldTerminate` для настоящего завершения остаётся в силе.

### 3. Единый переход из меню

Оба пункта передают выбранную роль одному обработчику. Порядок: скрыть конкретное окно поповера через его AppKit-ссылку; обеспечить обычный режим приложения; на следующем проходе главной очереди запросить активацию Companion и открыть сцену. Открытие не зависит от `didBecomeActive`: без основного окна macOS может не активировать приложение до отдельного нажатия Dock. Ожидание такого уведомления перед `openWindow` блокирует открытие и поэтому исключено. Ссылку на поповер получает маленький `NSViewRepresentable`-мост, без поиска по заголовкам или именам приватных классов и без отключения самой иконки строки меню.

До первого показа мост задаёт окну `.auxiliary` и `.moveToActiveSpace`: служебное окно остаётся на текущей сцене Stage Manager рядом с рабочими окнами. Взаимоисключающие `.primary`, `.canJoinAllApplications` и `.canJoinAllSpaces` снимаются; остальные настройки окна сохраняются. Это соответствует назначению [auxiliary в AppKit](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/auxiliary) для настроек и служебных панелей. Окна сохраняют обычный уровень и участие в Mission Control; `.transient` и глобальные настройки Stage Manager не используются.

Для нового окна финальный показ выполняется после получения его экземпляра мостом; системный запрос `activate(ignoringOtherApps: true)` повторяется перед `makeKeyAndOrderFront` и `orderFrontRegardless`. Фиксированных задержек нет. Отложенный запрос проверяет актуальность выбранной роли, экземпляра и состояния открытия. Для сохранённого экземпляра после `openWindow` выполняется явное завершение открытия без ожидания собственного `didBecomeKey`. Пока открытие первого окна ожидает регистрации, промежуточный пересчёт не отменяет переход в `.regular`. Повторные запросы одной роли объединяются; исходные уникальные сцены `Window` сохраняются. Открытие онбординга на старте проходит через тот же координатор без шага закрытия поповера.

Альтернатива — полагаться на автоматическую потерю фокуса поповером при `activate()`. Именно явного закрытия сейчас нет; нужен адресный переход с проверяемым порядком. Замена `MenuBarExtra` на ручной `NSStatusItem` для двух действий избыточна.

### 4. Возвращение из Dock использует существующие окна

Обработку повторной активации из Dock связать с координатором через делегат приложения. Предпочитать последнее активное открытое основное окно, а при его отсутствии выбирать существующее по стабильному порядку ролей. При необходимости развернуть и показать его; не создавать новое окно, если открытое уже существует. Это деталь реализации: при нескольких окнах контракт требует восстановить хотя бы одно.

Не переопределять обычное переключение фокуса между уже показанными окнами. Поведение запуска через закреплённую иконку при отсутствии открытых окон остаётся вне этого изменения.

### 5. Проверки состояния и реальная приёмка macOS

Выделить расчёт требуемого режима и порядок команд за тестируемой границей в `App/`; AppKit-вызовы подменяются в модульных тестах. Добавить узкий `AppTests`-таргет через `project.yml`, включающий только нужные файлы, без `@main` и каталога иконок; включить его в обе существующие тестовые схемы.

Проверить переходы ноль → одно → несколько → ноль окон, повторные события, переоткрытие прежнего экземпляра, запоздалые события, сворачивание/скрытие, онбординг, возврат из Dock и порядок «закрыть поповер → показать выбранное окно». Живой прогон на macOS 15.7 и 26 проверяет системное поведение, которое подмены не доказывают: Dock, фокус, восстановление, красную/жёлтую кнопки и ⌘W.

## Risks / Trade-offs

- Различия AppKit/SwiftUI между поддерживаемыми macOS → подтвердить переходы живой приёмкой на обеих границах; не считать модульные тесты доказательством работы Dock.
- Закрытие последнего окна и одновременное открытие другого могут вызвать мерцание Dock → сериализовать переходы на главном акторе и учитывать ожидающее открытие.
- Окно может сохраняться в памяти после закрытия → хранить состояние открытия отдельно от факта существования объекта, проверять повторное открытие.
- Поповер или sheet ошибочно удержит Dock → регистрировать только три основные роли, не подсчитывать все окна процесса.
- Смена политики или скрытие поповера может отнять фокус у целевого окна → активировать целевое окно после его регистрации, проверить переход при уже открытых и свёрнутых окнах.
- Существующий `onDisappear` онбординга может быть чувствителен к жизненному циклу SwiftUI → проверить, что новый мост не вызывает преждевременное завершение онбординга; не использовать этот callback для учёта Dock.

## Migration Plan

Миграция пользовательских данных не нужна. При реализации обновить README и синхронизировать дельту `menu-bar-ui`, включая ручное исправление её `Purpose`, где сейчас написано «без Dock» (дельта требований сама Purpose не меняет). После проверок архивировать change по процессу проекта. Откат возвращает прежнее управление окнами и соответствующее описание в спеках, не затрагивая настройки и журнал.
