# Основания статуса и тексты поповера

## Context

Мотивация и границы поведения — в [proposal.md](proposal.md) и [дельте menu-bar-ui](specs/menu-bar-ui/spec.md). Дизайн нужен, поскольку изменение затрагивает передачу оснований из Application в App и согласованность асинхронных проб.

`EgressClassifier` возвращает `protected(trace)` без сведений о выполненных критериях; сами критерии известны в `MonitoringCoordinator.runProbe`. `DetectorSnapshot` несёт последний `trace` и диагноз машины состояний, но не основание защиты или причину Offline. `StateMachine` обновляет `lastTrace` уже на первом leak-кандидате, до смены Protected на Leak. Поэтому форматирование последнего trace в UI не гарантирует достоверности.

`StatusPresentation` в `MenuBarPopover.swift` и `DetectorPresentation.stateText` независимо собирают подписи. Первая всегда добавляет IP, WARP и дата-центр при одном защищённом детекторе; вторая всегда добавляет IP и любой положительный WARP. Диагноз Leak иногда повторяется в баннере, при одном детекторе подзаголовок безусловно утверждает прямой выход. Причина Offline выводится по режиму защиты, Checking всегда объясняется сменой сети. `NetworkPathInfo` доступен координатору и содержит доступность пути.

Тестовые таргеты включают исходники напрямую: `ApplicationTests` уже включает весь Application и Domain, а `AppTests` — только `App/Windows`. Это позволяет проверять новую сборку текста без подключения всего SwiftUI-приложения и ассетов, несовместимых с тестовой сборкой на macOS 15.

## Goals / Non-Goals

**Цели:** разделить принятый вердикт и основание его показа; дать шапке и строкам единый источник текста; сохранить текущие решения о состоянии и группах; проверить содержательные комбинации без запуска реальной сети и Little Snitch.

**Вне задачи:** менять `ProbeResult` и его Codable-формат ради UI, переписывать машину состояний, добавлять историю причин Checking, подробную диагностику TLS/HTTP в меню, новые настройки, перерабатывать журнал и уведомления, менять окна, Dock или общий дизайн поповера.

## Decisions

### 1. Чистая модель выполненных критериев защиты

Добавить в Domain небольшое значение `ProtectionEvidence`: необязательный ожидаемый IP и учитываемое положительное значение WARP. Получать его через общий чистый расчёт рядом с `EgressClassifier`, используемый и классификацией, и сборкой оснований. Расчёт учитывает `acceptsWarp`, ожидаемые IP и приоритет обоих источников запрещённых адресов. Отсутствие основания не считается защитой. Существующие вердикты и `ProbeResult` сохраняются.

Таблица результата при отсутствии запрещённого совпадения:

| IP ожидаемый | WARP on/plus и учитывается | Основание |
| --- | --- | --- |
| Нет | Да | Только WARP |
| Да | Нет | Только IP |
| Да | Да | IP, затем WARP |
| Нет | Нет | Отсутствует |

Любое запрещённое совпадение даёт отсутствие основания защиты, включая одновременное совпадение с ожидаемым IP. `off`, `unknown`, выключенный флаг и `debugIgnoreWarp` не дают WARP-признака. Состояния `on` и `plus` сохраняются в тексте без нормализации.

Альтернатива — проверять настройки прямо из SwiftUI. Она не выбрана: правила дублируются, а изменённые настройки могут приписать старой пробе новое основание.

### 2. Отдельные данные принятого состояния в Application

Добавить к runtime и `DetectorSnapshot` типизированное пояснение состояния, например `DetectorStatusExplanation`: основание Protected, IP и диагноз Leak, либо причина Offline (`noNetwork`, `beaconUnavailable`, `unknown`). Checking использует нейтральный текст, Paused и выключенный детектор не требуют новых данных. Сырые `trace` и `diagnosis` остаются для существующих потребителей; новые тексты поповера не используют их как запасной источник неподтверждённых признаков.

Координатор вычисляет основание по тем же сохранённым критериям, с которыми выполнялась проба. Публикация состояния и пояснения выполняется согласованно, без промежуточного `publish` между ними и после проверки поколения пробы. Сверка конфигурации, влияющей на основание, нужна также после `await`, поскольку критерии могут измениться во время запроса.

Правила обновления:

- Принятая protected-проба обновляет основание, только если итоговое состояние Protected. Вердикт во сне, оставляющий строгий детектор в Checking, не показывается как защита.
- Первый leak-кандидат при ещё сохранённом Protected не меняет его пояснение. При переходе в Leak или новой принятой leak-пробе уже в Leak обновляются IP и диагноз утечки.
- При переходе в Offline скрываются прежние IP и WARP. Недоступный текущий путь означает `noNetwork`; принятая offline-проба при доступном пути — `beaconUnavailable`; без этих данных — `unknown`. Режим защиты причиной не является. На сетевых событиях пояснение пересчитывается вместе с состоянием, чтобы после возврата пути реактивный Offline не продолжал сообщать «нет сети».
- При Checking признаки предыдущего ответа скрываются. Для выхода из паузы, перезапуска и повторного включения используется новое основание только после принятой пробы.
- При изменении ожидаемых/запрещённых IP, учёта WARP, `debugIgnoreWarp`, маяка или прокси прежнее основание скрывается до новой принятой пробы. Проверяется именно конфигурация, влияющая на наблюдение и классификацию; переименование и изменение списка групп сами по себе основание не сбрасывают. Изменение динамического прямого IP также не должно приводить к показу признака, противоречащего актуальному запрещённому совпадению.

Не добавлять пробы, переходы или reconcile ради обновления текста. Если основания уже нет, UI показывает только статус до следующего существующего события. Сохранять старое основание в той же неизменённой конфигурации до двойного подтверждения — следствие текущей политики состояния; давность видна в строке «Проверка».

Альтернатива — менять `StateMachine.lastTrace`. Она затронула бы журнал, прямой IP guard и других потребителей; отдельная модель UI ограничивает влияние.

### 3. Общий форматировщик текста без SwiftUI

Вынести отбор и сборку текстов статуса в чистый компонент Application, по образцу существующего `HelperPresentation`. Его используют и `StatusPresentation`, и `DetectorPresentation.stateText`; цвета, символы, размеры и раскладка остаются в App. Этот компонент должен производить реальные строки шапки, строк детекторов и изменяемых баннеров, чтобы тесты проверяли используемый UI текст. Секция `MenuStatusPanel` принимает снапшот и настройки отдельно от действий меню и модели приложения: это позволяет отрисовать реальные компоненты на синтетических данных без запуска мониторинга.

Для Protected основание форматируется как `198.51.100.40`, `warp=on` или `198.51.100.40 · warp=plus`. Строка детектора добавляет префикс `защищён · `; шапка одного детектора использует само основание. При отсутствии основания строка — `защищён`, подзаголовок не выдумывает конкретный путь. При нескольких защищённых детекторах сводное сообщение шапки сохраняется, признаки остаются в отдельных строках.

Строчный регистр относится к подписям в блоке детекторов. Заголовки «Защищено», «Утечка» и остальные заголовки шапки сохраняются. Это продолжает существующий визуальный стиль; глобальная смена регистра не требуется. Показывать оба выполненных критерия — принятое в плане правило оформления.

### 4. Один диагноз утечки и точные тексты неопределённости

Leak: строка остаётся `утечка · IP`; шапка всегда использует диагноз, включая один детектор. Для `foreignEgress` текст сообщает несоответствие правилам защиты, поскольку произвольный чужой egress сам по себе не доказывает прямое подключение. Баннер больше не повторяет диагноз; сохраняет сведения о группах, владельце блокировки и условии снятия. В `observeOnly` баннер сообщает о режиме наблюдения без обещания снятия несуществующей блокировки.

Offline: причина одинакова для строгого и реактивного режима, меняется только отдельное пояснение о группах. Для строгого Offline заголовок баннера — «Закрыто — нет подтверждения защиты», вместо безусловного «Закрыто: сети нет». Под `observeOnly` утверждения о закрытии не выводятся.

Checking: «ждём подтверждения защиты» без фиксированного события-причины. Существующее пояснение о закрытии групп в строгом режиме сохраняется. Paused, выключенное состояние, действия и баннеры паузы не перерабатываются.

Альтернатива — подробные причины в каждой строке. Она добавляет повторы и увеличивает высоту поповера; для выбранной утечки диагноз принадлежит шапке.

### 5. Удалить только отображение строки сети

Убрать `DSInfoRow("Сеть", ...)` и неиспользуемое UI-форматирование сети. `NetworkPathInfo`, монитор пути, дедупликация, журнал сетевых событий и запуск перепроверок остаются прежними. Доступность пути нужна для честного Offline; тип интерфейса и шлюз не нужны в постоянном меню.

## Risks / Trade-offs

- Рассинхронизация пояснения после асинхронной пробы или настроек → проверки поколений и конфигурации, интеграционные сценарии на fake-пробах с управляемым завершением.
- Дублирование таблицы классификации → общий чистый расчёт признаков и построчные тесты, включая приоритет запрещённых адресов и debug-флаг.
- Изменение существующих потребителей `lastTrace` → оставить их контракт прежним и добавить независимые данные для UI.
- Краткий статус без основания после изменения конфигурации → допустим до новой принятой пробы; не заполнять его неподтверждёнными данными.
- Потеря диагностической строки сети → сведения по-прежнему обрабатываются монитором; отсутствие сети видно в Offline. Новый экран диагностики в эту задачу не входит.
- Пересечение с активным `manage-window-presence` в том же файле поповера → изменять только представление и инфо-строки, сохранить обработчики открытия окон и существующие требования Dock.

## Migration Plan

Миграция настроек, Keychain и журнала не нужна: пояснения существуют только в памяти. При реализации добавить чистую модель и тесты, затем доставку основания и форматирование, обновить превью затронутых состояний. `project.yml` менять только при фактической необходимости подключения тестов, `.xcodeproj` не коммитить.

После реализации выполнить проверки проекта и приёмку поповера при одном и нескольких детекторах, в обеих темах и при IPv6-ответе из синтетического тестового источника. Синхронизировать только дельту `menu-bar-ui`; остальные требования capability сохранить. Архивировать change после завершения по процессу проекта. Откат возвращает прежнее представление и соответствующую спецификацию без миграции пользовательских данных.
