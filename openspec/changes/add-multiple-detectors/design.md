# design — несколько детекторов

## Context

Мотивация — в proposal.md («Why»). Сейчас координатор (`MonitoringCoordinator`) владеет одной `StateMachine`, одним набором критериев и одним маппингом групп; `settings.leakGroups` протянут напрямую в reconcile, в `forceEnable` на сон и выход, в `FailsafeConfig` helper и в тексты уведомлений. Четыре слоя детектора делятся на два рода: растяжка и пробы описывают **путь** (и зависят от маяка, прокси и критериев), события сетевого пути и питания описывают **машину**; РУ-маяк с прямым IP — тоже факт о машине. Контракт helper — плоский список групп в `FailsafeConfig` — не знает о детекторах и менять его не нужно.

Ограничения: `Domain/` остаётся чистым Swift (арбитраж и классификация — доменные таблицы с построчными тестами); порог macOS 15.7 (`ProxyConfiguration` для URLSession и Network.framework доступна с macOS 14, гейт не требуется); адреса в тестах и макетах — только RFC 5737. Макеты согласованы и лежат в `design/app.pen`: вкладка «Детекторы», экран деталей, поповеры с блоком детекторов.

## Goals / Non-Goals

**Goals:**

- Детектор — конфигурация в Domain, рантайм в Application; N детекторов в одном координаторе с общими слоями.
- Арбитраж целевого состояния групп — чистая функция с таблицей, которую можно прочитать и проверить построчно.
- Один reconcile и одна failsafe-конфигурация на всех детекторов: helper и Little Snitch не узнают, что детекторов стало много.
- Существующий пользователь после обновления получает детектор «Основной» с прежними настройками и прежним поведением.

**Non-Goals:**

- Аутентификация прокси (логин и пароль, Keychain) — отдельный change.
- Полярность групп (allow-группы, включаемые при защите) — не нужна при принятом правиле арбитража.
- Разные интервалы (heartbeat, проба, таймаут) на детектор — общие.
- Несколько РУ-маяков или прямой IP на детектор — прямой IP один на машину.
- Изменение контракта helper.

## Decisions

### D1. Один координатор, N детекторных рантаймов

Координатор остаётся единственной точкой сериализации (D2 исходного design): он держит общие слои (монитор пути, монитор питания, РУ-маяк, пауза, завершение) и словарь рантаймов по `DetectorID`. Рантайм детектора — машина состояний, растяжка, цикл плановых проб, счётчик поколений проб, последний вердикт. Событие пути или питания раздаётся всем рантаймам; проба и обрыв растяжки адресованы одному.

Альтернатива — N координаторов: дублирует общие слои, а главное, разводит reconcile по N акторам, и арбитраж пришлось бы делать поверх них ещё одним актором с гонками между «мой reconcile» и «его reconcile». Отвергнута.

### D2. Арбитраж — чистая доменная таблица

`LeakPolicy.targetEnabledGroups(state, mode, mapping)` по-прежнему считается на детектор и отвечает «целевой набор или nil» для его групп. Новый `GroupArbiter` сводит ответы включённых детекторов в одну цель по группам:

| Желания детекторов, содержащих группу | Итог для группы |
| --- | --- |
| хотя бы один требует включить | включить (закрыто) |
| никто не требует включить, хотя бы один требует выключить | выключить (открыто) |
| ни один не определяет (все — nil) | не трогать |

Результат — пара множеств `enable` и `disable`; `managed` для `LeakPolicy.plan` — их объединение, поэтому группы «не трогать» в план не попадают, как сейчас не попадают группы вне маппинга. Выключенные детекторы в арбитраже не участвуют.

Отвергнуто: «включена, только если никто не выключает» (AND по включению) — спокойный детектор открывал бы группу, по которой другой только что подтвердил утечку, и ломал бы инвариант строгого режима. Отвергнута и полярность групп: при принятом правиле она не нужна.

### D3. Правила классификации — свойство детектора

`EgressCriteria` получает флаг «`warp=on` считается защитой» (по умолчанию `true`); ожидаемые и запрещённые IP — из детектора; прямой IP сети подставляет координатор во все критерии одинаково. Таблица классификации меняется в одной строке: `warp=on/plus` даёт Protected только при включённом флаге. Любой egress, не попавший ни под одно правило, остаётся утечкой — лояльного режима «всё, что не запрещено» нет, выход прокси по условию задачи известен заранее. Скрытый рычаг `debugIgnoreWarp` остаётся глобальным и накладывается на флаг детектора через И.

### D4. Маяк и формат ответа на детектор

Маяк детектора — основной и резервный URL плюс формат: `cdnCgiTrace` (plain text `key=value`, поля `ip=` и `warp=`) или `plainIP` (тело — IP-адрес, допустима JSON-строка `"<ip>"`). Разбор голого IP переезжает из `RuBeaconProber` в Domain и используется обоими; для `plainIP` `warp` считается `unknown`, и защиту определяют только ожидаемые адреса. Дефолт нового детектора — прежняя пара Cloudflare: `https://www.cloudflare.com/cdn-cgi/trace` и `https://1.1.1.1/cdn-cgi/trace`.

Альтернатива — один маяк на всех: не подходит, когда прокси детектора не пропускает конкретный домен или формат ответа другой.

### D5. Прокси через `ProxyConfiguration`

`ProxyConfig` детектора — вид (`httpConnect` | `socks5`), хост, порт. Проба: `URLSessionConfiguration.ephemeral` с `proxyConfigurations = [ProxyConfiguration(httpCONNECTProxy:)]` или `[ProxyConfiguration(socksv5Proxy:)]`. Растяжка: `NWParameters.tls` с теми же `proxyConfigurations`. Системные настройки прокси при этом не используются: детектор без прокси ходит напрямую, как сейчас. Резервный маяк по IP работает через прокси так же, как основной. Недоступный прокси для детектора — Offline: проба не дала ответа, утечки нет; в строгом режиме это закрывает группы детектора, что и требуется, если приложения умеют падать на прямое соединение при мёртвом прокси.

Альтернатива — `connectionProxyDictionary` (CFNetwork): устаревший словарь, не покрывает Network.framework для растяжки. Отвергнута.

### D6. Растяжка на детектор, опциональная

Растяжка детектора ходит на хост основного маяка и использует путь из его URL для heartbeat-запроса; обрыв или дедлайн чтения — немедленная проба этого детектора. Флаг «растяжка» в детекторе позволяет её выключить: через прокси сигнал обрыва описывает прокси, а не туннель, и пользователь может предпочесть только пробы. Смена сети сбрасывает backoff всех растяжек.

### D7. Общие слои и прямой IP

Монитор пути, монитор питания и РУ-маяк — по одному экземпляру. Смена пути инвалидирует пробы в полёте у всех детекторов и запускает пробу каждому после общего debounce; пропажа сети переводит все машины в Offline; засыпание и пробуждение раздаются всем. Прямой IP сети один и подставляется в запрещённые каждого детектора. `DirectIPGuard` сверяет кандидата с последним защищённым ответом **каждого** детектора: совпадение с любым означает, что РУ-запрос ушёл не напрямую, и кандидат отвергается; пока ни один детектор не дал вердикта, кандидат откладывается, как сейчас.

### D8. Режим на детектор, пауза общая, failsafe по объединению

Режим защиты — поле детектора, передаётся в его машину. Пауза и тумблер «Мониторинг» отправляют `userPaused`/`userResumed` всем машинам; строгие детекторы закрываются до остановки слоёв, как сейчас. Закрытие на засыпании и на завершении (`forceEnable` без листинга) берёт объединение групп включённых строгих детекторов; `FailsafeConfig.groups` — то же объединение, `strictActive` — «есть хотя бы один включённый строгий детектор и не `observeOnly`». Переключение режима детектора — переходный reconcile по объединённой цели, посчитанной уже с новым режимом; эффект на группы, разделённые с другими детекторами, определяется арбитражем, а не прежним правилом «открыть, если не Leak».

### D9. Выключение и удаление детектора открывают его группы

Выключенный детектор выходит из арбитража; его группы, которые не держит ни один другой детектор, выключаются (открываются) переходным reconcile — иначе пользователь остался бы запертым без агента, который снимет закрытие. Открытие выполняется и из Leak: детектор выключен пользователем, повторного Protected от него не будет; в журнал пишется предупреждение. Удаление детектора — то же самое плюс удаление конфигурации. Включение детектора — старт его рантайма: строгий закрывает до первой пробы.

### D10. Хранение: массив детекторов одним ключом, миграция один раз

`AppSettings.detectors: [DetectorConfig]` хранится в `UserDefaults` одним ключом `detectors` как JSON. Отдельные ключи на детектор не нужны: debug-рычаги остаются глобальными, а править массив через `defaults write` всё равно неудобно. Миграция при загрузке: если ключа `detectors` нет, из `expectedIPs`, `forbiddenEgressIPs`, `leakGroups`, `protectionMode` собирается детектор «Основной» (без прокси, маяк Cloudflare, `warp=on` считается защитой, растяжка включена) и записывается; старые ключи не удаляются, так что откат на прежнюю версию читает прежние значения. Нечитаемый JSON — предупреждение в журнал и один детектор «Основной» по дефолтам. Пустой массив допустим: мониторинг работает вхолостую, поповер говорит «детекторов нет».

### D11. Снапшот и UI

`MonitoringSnapshot` получает список снапшотов детекторов (имя, включён, состояние, вердикт, диагноз, давность проверки, активна ли растяжка) и сводное состояние — худшее среди включённых по порядку Leak > Checking > Offline > Protected; Paused, когда мониторинг на паузе; без включённых детекторов — Offline с подписью. Иконка меню-бара и шапка поповера берут сводное; баннер — у худшего детектора; блок детекторов в поповере — по строке на каждый, включая выключенные. `activeLeakGroups` — множество `enable` последнего успешного арбитража.

### D12. Журнал, уведомления, имена

`JournalEvent` получает необязательное поле `detector` (имя); отображение — префикс «[имя]» перед текстом, старые записи без поля читаются как есть. Уведомления об утечке и восстановлении называют детектор в заголовке. Имя детектора — любая непустая строка, уникальность не требуется: идентификатор — `DetectorID` (UUID).

### D13. Тесты

Domain: таблица арбитража построчно (включая «не трогать», выключенный детектор, группа в трёх детекторах), классификация с флагом `warp=on` и форматом `plainIP`, `DirectIPGuard` с несколькими ответами. Application: координатор с двумя детекторами — утечка одного при защите другого закрывает только его группы, общая группа остаётся закрытой, пока закрыта хоть одним; выключение детектора открывает эксклюзивные группы; пауза закрывает строгие; `forceEnable` и `FailsafeConfig` по объединению; миграция настроек. Infrastructure: сборка `ProxyConfiguration` из `ProxyConfig`, разбор обоих форматов маяка, хост и путь растяжки из URL.

## Risks / Trade-offs

- [SOCKS5 без удалённого разрешения имён: имя маяка резолвится локально, DNS-запрос уходит мимо прокси] → резервный маяк по IP проверяет путь без DNS; живая проверка на стадии apply (см. «Живая проверка прокси») показала, что риск не реализуется: и URLSession, и Network.framework передают SOCKS5-прокси имя хоста.
- [N растяжек и N проб — больше соединений и трафика] → растяжка опциональна; интервалы общие и ограничены снизу, как сейчас.
- [Строгий детектор в Offline держит закрытой группу, общую с защищённым детектором] → так и задумано правилом арбитража; подпись «также в …» у группы в деталях детектора делает причину видимой, строка «Группы LS» в поповере показывает факт.
- [Выход резидентного прокси сменился — детектор уходит в Leak] → по условию задачи выход известен; пользователь обновляет ожидаемые IP, диагноз в журнале называет egress.
- [Миграция прочитала не то, что ожидал пользователь] → старые ключи остаются, запись в журнал о миграции с составом детектора «Основной».
- [Переходный reconcile при выключении детектора открывает группу, которую пользователь закрыл руками в Little Snitch] → трогаются только группы из маппинга выключенного детектора, как и при любом reconcile.

## Живая проверка прокси (п. 4.3, 2026-10-24)

Целевая машина (macOS 26, за WARP), локальные SOCKS5 и HTTP CONNECT на 127.0.0.1, логирующие запрос CONNECT; `Scripts/live-check.swift` с `--socks5`/`--http-connect` и боевые `BeaconProber` и `TripwirePool`:

- Проба через SOCKS5 и HTTP CONNECT доходит до маяка через прокси: в логе прокси по CONNECT на пробу и на растяжку. Egress маяка — выход прокси (у локального прокси он совпадает с выходом машины; проверка с удалённым резидентным прокси — в живой приёмке п. 7.2).
- **DNS при SOCKS5:** URLSession с `ProxyConfiguration(socksv5Proxy:)` и `NWConnection` с тем же прокси через `PrivacyContext` шлют CONNECT с `ATYP=domain` (`www.cloudflare.com:443`) — имя разрешает прокси, локального разрешения для пути к маяку нет. Резервный маяк по IP уходит с `ATYP=IPv4`.
- Мёртвый прокси (порт без слушателя): проба — `NSURLErrorCannotConnectToHost` → Offline (`networkFailure`), не утечка. `NWConnection` растяжки при этом переходит в `.waiting(Connection refused)`, а не в `.failed`, — растяжка трактует ожидание как обрыв, гасит соединение и переустанавливается с backoff (за 9 с — три обрыва: сразу, через 2 и 4 с). Без этого она висела бы в подключении без сигнала и без backoff.

## Migration Plan

1. Код и спеки одним PR; helper не меняется, переустановка демона не нужна.
2. Первый запуск новой версии: ключа `detectors` нет → собирается «Основной» из старых ключей, пишется в defaults, в журнал — запись о миграции. Поведение идентично прежнему.
3. Онбординг и подстановка дефолтной группы «VPN down» работают с детектором «Основной».
4. Откат: прежняя версия читает старые ключи, которые миграция не трогала; изменения, сделанные в новой версии в других детекторах, при откате теряются.

## Open Questions

- Аутентификация прокси: нужна ли и когда — отдельный change с Keychain.
- Heartbeat растяжки для маяка формата `plainIP` с нестандартным путём: пока путь берётся из URL основного маяка; если сервис не отвечает на keep-alive, растяжку для такого детектора выключают.
