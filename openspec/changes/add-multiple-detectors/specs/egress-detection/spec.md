# Spec Delta

## MODIFIED Requirements

### Requirement: Классификация результата пробы маяка

Система SHALL классифицировать каждую пробу маяка детектора по правилам этого детектора: его ожидаемым IP (`EXPECTED_IPS`), его запрещённым IP вместе с общим прямым IP сети (вместе — `FORBIDDEN_EGRESS` детектора) и его флагу «`warp=on` считается защитой» (по умолчанию включён). Denylist сильнее всех прочих признаков:

1. ответ с адресом, ip ∈ `FORBIDDEN_EGRESS` (при любом `warp=`) → leak-кандидат с диагнозом по источнику совпадения;
2. ответ с адресом, `warp ∈ {on, plus}`, флаг «`warp=on` считается защитой» включён, ip ∉ `FORBIDDEN_EGRESS` → protected;
3. ответ с адресом, ip ∈ `EXPECTED_IPS`, ip ∉ `FORBIDDEN_EGRESS` → protected при любом `warp=`, в том числе когда поля `warp=` в ответе нет;
4. ответ с адресом, не подпавший под правила 1–3 → leak-кандидат;
5. таймаут, сетевой сбой, TLS-ошибка, недоступный прокси детектора или ответ без адреса (captive portal) → offline.

Правила SHALL применяться одинаково к маякам обоих форматов (см. «Формат ответа маяка»); для ответа без поля `warp=` правило 2 не выполняется никогда. Правила одного детектора SHALL NOT влиять на классификацию проб другого.

#### Scenario: Защищённый egress через WARP

- **WHEN** у детектора включён флаг «`warp=on` считается защитой» и проба вернула `warp=on` с ip, отсутствующим в `FORBIDDEN_EGRESS`
- **THEN** результат пробы — protected

#### Scenario: warp=on не считается защитой

- **WHEN** у детектора выключен флаг «`warp=on` считается защитой», проба вернула `warp=on`, а ip не входит ни в `EXPECTED_IPS`, ни в `FORBIDDEN_EGRESS`
- **THEN** результат пробы — leak-кандидат: для этого детектора путь через WARP — чужой путь

#### Scenario: Чужой egress без WARP

- **WHEN** проба вернула `warp=off` и ip, отсутствующим и в `EXPECTED_IPS`, и в `FORBIDDEN_EGRESS`
- **THEN** результат пробы — leak-кандидат

#### Scenario: Egress из EXPECTED_IPS без WARP

- **WHEN** проба вернула `warp=off` или ответ без поля `warp=`, а ip ∈ `EXPECTED_IPS` детектора
- **THEN** результат пробы — protected

#### Scenario: Запрещённый egress перевешивает warp=on

- **WHEN** проба вернула `warp=on`, но ip ∈ запрещённым IP детектора (сервер инфраструктуры или сам прокси-сервер)
- **THEN** результат пробы — leak-кандидат с диагнозом «цепочка вышла напрямую с сервера <ip>»

#### Scenario: Egress совпал с прямым РУ-IP

- **WHEN** проба любого детектора вернула ip, равный текущему прямому IP сети
- **THEN** результат пробы — leak-кандидат с диагнозом «полный обход VPN: трафик идёт с прямого IP сети»

#### Scenario: Правила разных детекторов независимы

- **WHEN** один и тот же egress-IP входит в `EXPECTED_IPS` детектора A и не входит в `EXPECTED_IPS` детектора B, флаг `warp=on` у обоих выключен
- **THEN** проба A классифицируется как protected, проба B — как leak-кандидат

#### Scenario: Captive portal или недоступный маяк

- **WHEN** проба завершилась таймаутом, сетевой/TLS-ошибкой, отказом прокси или вернула ответ без адреса
- **THEN** результат пробы — offline (НЕ утечка)

### Requirement: Резервный маяк

Система SHALL при недоступности основного маяка детектора выполнять пробу через его резервный маяк (по умолчанию `https://1.1.1.1/cdn-cgi/trace`, обращение по IP без DNS) тем же путём, что и основной — через тот же прокси или напрямую, — прежде чем классифицировать результат как offline. Резервный маяк SHALL быть необязательным: у детектора без резервного маяка недоступность основного даёт offline.

#### Scenario: Основной маяк недоступен, резервный отвечает

- **WHEN** основной маяк детектора не ответил за таймаут, а резервный вернул валидный ответ
- **THEN** классификация выполняется по ответу резервного маяка по правилам того же детектора

#### Scenario: Резервный маяк не задан

- **WHEN** у детектора нет резервного маяка и основной не ответил за таймаут
- **THEN** результат пробы — offline без дополнительных запросов

### Requirement: Растяжка — постоянное соединение с heartbeat

Для каждого включённого детектора с включённой растяжкой система SHALL поддерживать постоянное TLS-соединение к хосту его основного маяка («растяжка») тем же путём, что и пробы детектора (через его прокси или напрямую), раз в `heartbeatSeconds` (15 с, общее для всех детекторов) отправлять по нему минимальный запрос `GET <путь основного маяка>` с `Connection: keep-alive` и дедлайном чтения 5 с. Любой обрыв соединения (EOF/RST/ошибка) или истечение дедлайна SHALL немедленно запускать свежую пробу этого детектора. Переустановка растяжки после обрыва SHALL выполняться с экспоненциальным backoff (2 с → 4 → 8 → … максимум 60 с). Растяжка SHALL быть отключаемой на детектор: у детектора с выключенной растяжкой работают только пробы.

#### Scenario: Обрыв растяжки

- **WHEN** TLS-соединение растяжки детектора получает EOF, RST или ошибку
- **THEN** немедленно запускается свежая проба этого детектора и начинается переустановка его растяжки с backoff; растяжки и состояния других детекторов не затрагиваются

#### Scenario: Heartbeat не дождался ответа

- **WHEN** ответ на heartbeat-запрос не получен за 5 с
- **THEN** соединение считается мёртвым, запускается немедленная свежая проба этого детектора

#### Scenario: Backoff в офлайне

- **WHEN** переустановка растяжки повторно завершается ошибкой
- **THEN** интервалы попыток растут экспоненциально от 2 с до максимума 60 с

#### Scenario: Растяжка выключена у детектора

- **WHEN** у детектора выключена растяжка
- **THEN** постоянное соединение для него не устанавливается, детектор наблюдается плановыми пробами, событиями пути и питания

### Requirement: Плановая свежая проба

Система SHALL раз в `probeSeconds` (60 с, общее для всех детекторов) выполнять для каждого включённого детектора свежую пробу его маяка отдельным новым соединением без кэша и переиспользования соединений, через прокси детектора, с таймаутом `probeTimeoutSeconds` (6 с). Это ловит случай «старый поток жив, новые соединения идут мимо VPN», который растяжка не видит.

#### Scenario: Тихая утечка при живой растяжке

- **WHEN** маршруты перевернулись так, что старые соединения живут по старому пути, а новые идут напрямую
- **THEN** не позднее чем через ~60 с плановая проба детектора новым соединением обнаруживает leak-кандидата

#### Scenario: Плановые пробы идут у каждого детектора

- **WHEN** включены два детектора с разными прокси
- **THEN** каждый плановый цикл выполняет по пробе на детектор, каждую — через прокси своего детектора

### Requirement: РУ-маяк — автоопределение прямого IP

Система SHALL периодически запрашивать «прямой IP» текущей сети у РУ-маяка (конфигурируемые URL; домен обязан быть в зоне `.ru`): основной `https://yandex.ru/internet/api/v0/ip` (JSON-строка `"<ip>"`), резервный `https://2ip.ru` (text/plain, требуется curl-подобный User-Agent). Запрос SHALL идти напрямую, без прокси какого-либо детектора. Ответ SHALL валидироваться как IP-адрес (v4/v6), иначе отбрасывается. Запрос выполняется при старте, при каждой фактической смене сети (повторные события пути без смены сведений дедуплицируются и запрос не порождают) и далее раз в `ruBeaconRefreshSeconds` (300 с). Полученный прямой IP один на машину: он образует динамическую часть `FORBIDDEN_EGRESS` каждого детектора и живёт до следующей фактической смены сети.

#### Scenario: Прямой IP получен

- **WHEN** РУ-маяк вернул валидный IP-адрес
- **THEN** адрес становится динамической частью `FORBIDDEN_EGRESS` всех детекторов и немедленно запускается свежая проба каждого включённого детектора

#### Scenario: Невалидный ответ РУ-маяка

- **WHEN** тело ответа РУ-маяка после разбора не является IP-адресом
- **THEN** результат отбрасывается, динамическая запись не обновляется

#### Scenario: Основной РУ-маяк недоступен

- **WHEN** основной РУ-маяк не ответил за таймаут 6 с
- **THEN** выполняется запрос к резервному РУ-маяку

#### Scenario: Повторное событие пути не трогает прямой IP

- **WHEN** прямой РУ-IP известен и приходит событие пути со сведениями, идентичными предыдущим
- **THEN** прямой IP остаётся в denylist без сброса и повторного запроса, повторной записи в журнал нет

### Requirement: Guard от РУ-маяка, прошедшего через VPN

Система SHALL NOT добавлять ответ РУ-маяка в denylist, если он совпал с последним защищённым egress хотя бы одного детектора (`warp=on` либо адрес из его `EXPECTED_IPS`): это означает, что `.ru` не в сплите и запрос ушёл не напрямую. В журнал SHALL записываться предупреждение. Пока ни один детектор не дал вердикта, кандидат SHALL откладываться до первого вердикта.

#### Scenario: РУ-маяк вернул protected-egress

- **WHEN** ответ РУ-маяка равен последнему защищённому egress-IP любого детектора
- **THEN** запись в denylist не добавляется, в журнал пишется предупреждение «РУ-маяк прошёл через VPN, сплит не работает?»

#### Scenario: Совпадение только с незащищённым ответом

- **WHEN** ответ РУ-маяка равен egress-IP детектора, чей последний вердикт — утечка
- **THEN** кандидат принимается: совпадение с утечкой подтверждает, что это прямой IP

## ADDED Requirements

### Requirement: Детектор как единица наблюдения

Система SHALL поддерживать набор детекторов. Детектор SHALL описываться: именем; признаком «включён»; режимом защиты; основным и резервным маяком с форматом ответа; прокси (нет / HTTP CONNECT / SOCKS5 с хостом и портом); флагом «`warp=on` считается защитой»; списками ожидаемых и запрещённых IP; признаком «растяжка включена»; списком rule groups. У каждого включённого детектора SHALL быть собственные растяжка (если включена), пробы и вердикт. Выключенный детектор SHALL NOT ходить в сеть и SHALL NOT влиять на группы.

#### Scenario: Два пути, два вердикта

- **WHEN** включены детектор без прокси и детектор через SOCKS5, и прокси перестал туннелировать
- **THEN** детектор через прокси фиксирует утечку по своим правилам, детектор без прокси остаётся защищённым

#### Scenario: Выключенный детектор молчит

- **WHEN** детектор выключен пользователем
- **THEN** его растяжка остановлена, пробы не выполняются, вердикта у него нет, в арбитраже групп он не участвует

### Requirement: Проба и растяжка через прокси

Проба и растяжка детектора SHALL ходить через его прокси, если он задан: HTTP CONNECT или SOCKS5 по хосту и порту, без аутентификации. Детектор без прокси SHALL ходить напрямую; системные настройки прокси macOS SHALL NOT использоваться ни в одном случае. Недоступность или отказ прокси SHALL классифицироваться как offline этого детектора, а не как утечка.

#### Scenario: Egress через прокси

- **WHEN** у детектора задан SOCKS5-прокси и проба выполнена
- **THEN** маяк отвечает адресом выхода прокси, а не адресом машины

#### Scenario: Прокси недоступен

- **WHEN** соединение с прокси детектора отклонено или не установилось за таймаут
- **THEN** результат пробы — offline; в строгом режиме детектора его группы закрываются, утечка не фиксируется

#### Scenario: Детектор без прокси не зависит от системного прокси

- **WHEN** в macOS настроен системный прокси, а у детектора прокси не задан
- **THEN** проба и растяжка идут напрямую, системный прокси не используется

### Requirement: Формат ответа маяка

Маяк детектора SHALL иметь один из двух форматов ответа: `cdn-cgi/trace` (plain text `key=value` по строкам со значимыми полями `ip=` и `warp=`; такой ответ отдаёт любой домен за Cloudflare) или «голый IP» (тело ответа — IP-адрес, допустима JSON-строка `"<ip>"`). Ответ SHALL валидироваться: адрес обязан разбираться как IPv4 или IPv6, иначе проба — offline. У формата «голый IP» состояние `warp` SHALL считаться неизвестным.

#### Scenario: Маяк формата голый IP

- **WHEN** маяк детектора вернул тело `"198.51.100.40"` в формате JSON-строки
- **THEN** адрес разбирается как `198.51.100.40`, `warp` неизвестен, классификация идёт по ожидаемым и запрещённым IP детектора

#### Scenario: Голый IP не разобрался

- **WHEN** маяк формата «голый IP» вернул HTML-страницу
- **THEN** результат пробы — offline

#### Scenario: Trace с другого домена за Cloudflare

- **WHEN** основной маяк детектора — `/cdn-cgi/trace` домена, отличного от cloudflare.com
- **THEN** ответ разбирается по тем же полям `ip=` и `warp=`, что и у маяка по умолчанию

### Requirement: Общие слои раздаются всем детекторам

События сетевого пути, события системного питания и РУ-маяк SHALL существовать в одном экземпляре на приложение и раздаваться всем включённым детекторам. Фактическая смена пути SHALL инвалидировать пробы в полёте у всех детекторов и после общего debounce запускать пробу каждого; пропажа сети SHALL переводить все детекторы в Offline; засыпание и пробуждение SHALL обрабатываться каждым детектором по его режиму.

#### Scenario: Смена сети пробует все детекторы

- **WHEN** сетевой путь изменился при живой сети и включены три детектора
- **THEN** после одного debounce выполняется по пробе на каждый детектор, вердикты проб, ушедших до смены пути, отбрасываются у всех

#### Scenario: Пропажа сети гасит все детекторы

- **WHEN** путь стал unsatisfied
- **THEN** каждый включённый детектор переходит в Offline; строгие закрывают свои группы

#### Scenario: Засыпание закрывает строгие детекторы

- **WHEN** система сообщает о предстоящем засыпании и среди включённых есть строгие и реактивные детекторы
- **THEN** группы строгих детекторов включаются до подтверждения сна, группы реактивных не трогаются
