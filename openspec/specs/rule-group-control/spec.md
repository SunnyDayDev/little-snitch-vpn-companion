# rule-group-control

## Purpose

Управление rule groups Little Snitch: привилегированный helper-демон (root) как единственная точка вызова `littlesnitch` CLI, узкий XPC-контракт с валидацией клиента, получение списка групп и применение настраиваемого маппинга «состояние → включённые группы».

## Requirements

### Requirement: Helper — единственная точка вызова littlesnitch

Все обращения к `littlesnitch` CLI (`/Applications/Little Snitch.app/Contents/Components/littlesnitch`, работает только под root) SHALL выполняться исключительно привилегированным helper-демоном (LaunchDaemon через `SMAppService.daemon`). Приложение SHALL NOT вызывать CLI напрямую.

#### Scenario: Включение группы

- **WHEN** приложению нужно включить rule group
- **THEN** оно вызывает helper по XPC, и helper выполняет `littlesnitch rulegroup -e <имя>`

### Requirement: Узкий XPC-контракт

XPC-интерфейс helper SHALL оставаться узким и перечислимым: версия helper; список rule groups (имя + enabled-состояние, JSON); включение/выключение rule group по имени; установка failsafe-конфигурации (активность строгого режима, список групп, таймаут супервизии). Произвольные команды SHALL NOT проходить по построению интерфейса.

#### Scenario: Запрос списка групп

- **WHEN** приложение вызывает операцию списка групп
- **THEN** helper выполняет `littlesnitch export-model`, выборочно парсит модель и возвращает только имена и enabled-состояния групп

#### Scenario: Запрос версии

- **WHEN** приложение вызывает операцию версии
- **THEN** helper возвращает строку версии для отображения в UI

#### Scenario: Передача failsafe-конфигурации

- **WHEN** пользователь включает строгий режим или меняет список управляемых групп
- **THEN** приложение передаёт helper актуальную failsafe-конфигурацию одной операцией XPC

### Requirement: Валидация XPC-клиента

Helper SHALL валидировать подключающегося XPC-клиента по code-signing requirement (audit token → проверка кода; requirement — тот же сертификат подписи + bundle id приложения) и SHALL отклонять соединения, не прошедшие проверку.

#### Scenario: Чужой клиент

- **WHEN** к Mach-сервису helper подключается процесс, не удовлетворяющий code-signing requirement
- **THEN** helper отклоняет соединение и не выполняет операций

### Requirement: Таймаут и деградация CLI

Вызов CLI из helper SHALL ограничиваться таймаутом 3 с. Отсутствие CLI, ошибка или таймаут SHALL приводить к: флагу «helper недоступен», уведомлению об ошибке, записи в журнал; при активном Leak — к эскалации (см. failsafe-escalation). Неудача парсинга `export-model` SHALL давать внятную ошибку, не падение.

#### Scenario: CLI не отвечает

- **WHEN** `littlesnitch` не завершился за 3 с
- **THEN** операция возвращает ошибку, взводится флаг «helper недоступен», пишется журнал и отправляется уведомление

#### Scenario: Формат export-model изменился

- **WHEN** JSON `export-model` не удаётся распарсить
- **THEN** возвращается внятная ошибка, приложение продолжает работать

### Requirement: Настраиваемый маппинг состояние → группы

Система SHALL поддерживать настраиваемый маппинг «состояние → какие rule groups включены», являющийся функцией режима защиты:

- **Реактивный режим** (по умолчанию): Leak → включить выбранные пользователем группы (`leakGroups`); Protected → выключить их; Offline, Checking и Paused → ничего не менять;
- **Строгий режим**: Protected → выключить группы; все прочие состояния (Leak, Offline, Checking, Paused) → включить группы.

Применение — только через reconcile.

#### Scenario: Применение маппинга при Leak

- **WHEN** состояние стало Leak и в маппинге выбраны группы
- **THEN** reconcile включает каждую выбранную группу, фактическое состояние которой «выключена»

#### Scenario: Offline не трогает группы в реактивном режиме

- **WHEN** режим реактивный и состояние стало Offline
- **THEN** никакие rule groups не включаются и не выключаются

#### Scenario: Offline закрывает в строгом режиме

- **WHEN** режим строгий и состояние стало Offline
- **THEN** reconcile включает каждую группу маппинга, фактическое состояние которой «выключена»

### Requirement: Список групп в настройках

Приложение SHALL получать список rule groups (имя + текущее состояние) через helper и отображать в настройках с чекбоксом «включать при утечке» у каждой. Список SHALL обновляться при открытии вкладки и по кнопке «Обновить список из LS».

#### Scenario: Открытие вкладки Группы

- **WHEN** пользователь открывает вкладку «Группы» в настройках
- **THEN** приложение запрашивает у helper актуальный список групп и отображает его с чекбоксами

#### Scenario: Несуществующее имя группы в маппинге

- **WHEN** reconcile пытается включить группу, имени которой нет в LS
- **THEN** в журнал пишется внятная ошибка, отправляется уведомление, приложение не падает

### Requirement: Приложение не модифицирует правила LS

Система SHALL только включать/выключать rule groups по имени. Создание, изменение и удаление групп и правил SHALL оставаться за пользователем в UI Little Snitch. Механизм профилей LS (`profile -a/-d`) SHALL NOT использоваться.

#### Scenario: Границы вмешательства

- **WHEN** приложению нужно заблокировать запрещённые приложения
- **THEN** оно только включает существующую rule group и никогда не создаёт/не правит правила

### Requirement: Персистентная failsafe-конфигурация helper

Helper SHALL персистить failsafe-конфигурацию (активность строгого режима, список групп, таймаут супервизии) в root-доступном месте (`/Library/Application Support/<label>/`), переживающем перезапуски helper и перезагрузку ОС. Helper SHALL NOT читать user defaults приложения. При неактивном строгом режиме failsafe-логика helper SHALL быть полностью выключена, а поведение helper — идентично текущему.

#### Scenario: Конфигурация переживает перезагрузку

- **WHEN** строгий режим включён, машина перезагружена и helper запустился заново
- **THEN** helper читает свою персистентную конфигурацию и знает режим и список групп без обращения к приложению

#### Scenario: Реактивный режим не меняет поведение helper

- **WHEN** failsafe-конфигурация помечает строгий режим неактивным
- **THEN** helper не выполняет ни супервизии соединений, ни закрытия на загрузке — поведение идентично версии без failsafe

### Requirement: Dead-man's switch — закрытие при исчезновении приложения

При активном строгом режиме helper SHALL отслеживать XPC-соединения приложения (обработчики invalidation) и, если все соединения пропали и не восстановились за таймаут супервизии, SHALL включить группы из failsafe-конфигурации. Механизм SHALL покрывать крэш и kill -9 приложения; штатный выход приложение дополнительно закрывает само (см. state-machine), helper — страховка. Переустановка/обновление helper SHALL NOT приводить к ложному срабатыванию.

#### Scenario: Крэш приложения

- **WHEN** строгий режим активен, состояние Protected (группы выключены) и процесс приложения убит kill -9
- **THEN** не позднее таймаута супервизии helper включает группы из failsafe-конфигурации

#### Scenario: Быстрый перезапуск приложения

- **WHEN** строгий режим активен и приложение перезапустилось быстрее таймаута супервизии
- **THEN** группы не трогаются helper'ом — новое соединение отменяет таймер

### Requirement: Закрытие групп на загрузке ОС

При активном строгом режиме helper SHALL запускаться на загрузке ОС (RunAtLoad) и включать группы из failsafe-конфигурации до логина пользователя и старта приложения, с повторными попытками, пока `littlesnitch` CLI не станет доступен. Закрытие SHALL выполняться только в первые минуты после загрузки (гейт по uptime): перезапуск демона посреди сессии не должен закрывать группы поверх живого приложения со свежим Protected-вердиктом. Это закрывает окно «power loss при открытых группах → загрузка с открытым трафиком».

#### Scenario: Загрузка после аварийного выключения

- **WHEN** строгий режим активен, машина выключилась аварийно при выключенных группах и загружается
- **THEN** helper при старте системы включает группы до логина пользователя

#### Scenario: CLI ещё недоступен на раннем этапе загрузки

- **WHEN** helper стартовал на загрузке, а `littlesnitch` CLI ещё не отвечает
- **THEN** helper повторяет попытки с нарастающим интервалом до успеха, не завершаясь по первой ошибке

#### Scenario: Перезапуск демона посреди сессии не закрывает

- **WHEN** строгий режим активен, приложение живо в состоянии Protected и helper перезапущен (переустановка)
- **THEN** helper не включает группы при старте: uptime выше порога загрузки, закрытие на старте пропускается
