# egress-detection

## Purpose

Детекция фактического egress машины: определяет, уходит ли foreign-трафик через VPN-цепочку (маяк видит `warp=on`), путём трёхслойного наблюдения — постоянная растяжка, события сетевого пути, периодические пробы — плюс РУ-маяк для автоопределения прямого IP и denylist запрещённого egress.

## Requirements

### Requirement: Классификация результата пробы маяка

Система SHALL классифицировать каждую пробу foreign-маяка (`https://www.cloudflare.com/cdn-cgi/trace`, резервный `https://1.1.1.1/cdn-cgi/trace`; ответ — plain text `key=value` со значимыми полями `ip=`, `warp=`) по правилам, где denylist `FORBIDDEN_EGRESS` сильнее всех прочих признаков:

1. HTTP 200 с `ip=`, ip ∈ `FORBIDDEN_EGRESS` (при любом `warp=`) → leak-кандидат с диагнозом по источнику совпадения;
2. HTTP 200 с `ip=`, `warp ∈ {on, plus}`, ip ∉ `FORBIDDEN_EGRESS` → protected;
3. HTTP 200 с `ip=`, `warp=off`, ip ∈ `EXPECTED_IPS`, ip ∉ `FORBIDDEN_EGRESS` → protected;
4. HTTP 200 с `ip=`, `warp=off`, ip чужой → leak-кандидат;
5. Таймаут, сетевой сбой, TLS-ошибка или ответ без `ip=` (captive portal) → offline.

#### Scenario: Защищённый egress через WARP

- **WHEN** проба вернула HTTP 200 с `warp=on` и ip, отсутствующим в `FORBIDDEN_EGRESS`
- **THEN** результат пробы — protected

#### Scenario: Чужой egress без WARP

- **WHEN** проба вернула HTTP 200 с `warp=off` и ip, отсутствующим и в `EXPECTED_IPS`, и в `FORBIDDEN_EGRESS`
- **THEN** результат пробы — leak-кандидат

#### Scenario: Egress из EXPECTED_IPS без WARP

- **WHEN** проба вернула HTTP 200 с `warp=off` и ip ∈ `EXPECTED_IPS`
- **THEN** результат пробы — protected

#### Scenario: Запрещённый egress перевешивает warp=on

- **WHEN** проба вернула HTTP 200 с `warp=on`, но ip ∈ статической части `FORBIDDEN_EGRESS` (сервер инфраструктуры)
- **THEN** результат пробы — leak-кандидат с диагнозом «цепочка вышла напрямую с сервера <ip>»

#### Scenario: Egress совпал с прямым РУ-IP

- **WHEN** проба вернула HTTP 200 с ip, равным текущему динамическому прямому РУ-IP
- **THEN** результат пробы — leak-кандидат с диагнозом «полный обход VPN: foreign-трафик идёт с прямого IP сети»

#### Scenario: Captive portal или недоступный маяк

- **WHEN** проба завершилась таймаутом, сетевой/TLS-ошибкой или вернула ответ без поля `ip=`
- **THEN** результат пробы — offline (НЕ утечка)

### Requirement: Резервный маяк

Система SHALL при недоступности основного маяка выполнять пробу через резервный (`https://1.1.1.1/cdn-cgi/trace`, обращение по IP без DNS) прежде чем классифицировать результат как offline.

#### Scenario: Основной маяк недоступен, резервный отвечает

- **WHEN** основной маяк не ответил за таймаут, а резервный вернул валидный ответ
- **THEN** классификация выполняется по ответу резервного маяка

### Requirement: Растяжка — постоянное соединение с heartbeat

Система SHALL поддерживать постоянное TLS-соединение к маяку («растяжка»), раз в `heartbeatSeconds` (15 с) отправлять по нему минимальный запрос `GET /cdn-cgi/trace` с `Connection: keep-alive` и дедлайном чтения 5 с. Любой обрыв соединения (EOF/RST/ошибка) или истечение дедлайна SHALL немедленно запускать свежую пробу. Переустановка растяжки после обрыва SHALL выполняться с экспоненциальным backoff (2 с → 4 → 8 → … максимум 60 с).

#### Scenario: Обрыв растяжки

- **WHEN** TLS-соединение растяжки получает EOF, RST или ошибку
- **THEN** немедленно запускается свежая проба маяка и начинается переустановка растяжки с backoff

#### Scenario: Heartbeat не дождался ответа

- **WHEN** ответ на heartbeat-запрос не получен за 5 с
- **THEN** соединение считается мёртвым, запускается немедленная свежая проба

#### Scenario: Backoff в офлайне

- **WHEN** переустановка растяжки повторно завершается ошибкой
- **THEN** интервалы попыток растут экспоненциально от 2 с до максимума 60 с

### Requirement: Реакция на события сетевого пути

Система SHALL наблюдать изменения сетевого пути (интерфейсы, шлюз, появление/исчезновение utun) и на любое изменение запускать немедленную пробу с debounce ~300 мс от шквала событий.

#### Scenario: Смена сети

- **WHEN** сетевой путь изменился (например, отключение VPN-интерфейса utun)
- **THEN** после debounce ~300 мс запускается немедленная свежая проба

#### Scenario: Шквал событий пути

- **WHEN** за 300 мс приходит несколько событий изменения пути
- **THEN** выполняется одна проба, а не по одной на каждое событие

### Requirement: Плановая свежая проба

Система SHALL раз в `probeSeconds` (60 с) выполнять свежую пробу отдельным новым соединением без кэша и переиспользования соединений, с таймаутом `probeTimeoutSeconds` (6 с). Это ловит случай «старый поток жив, новые соединения идут мимо VPN», который растяжка не видит.

#### Scenario: Тихая утечка при живой растяжке

- **WHEN** маршруты перевернулись так, что старые соединения живут по старому пути, а новые идут напрямую
- **THEN** не позднее чем через ~60 с плановая проба новым соединением обнаруживает leak-кандидата

### Requirement: Двойное подтверждение утечки

Система SHALL переводить детектор в состояние Leak только после двух leak-проб подряд с интервалом 2–3 с. Protected подтверждения NOT REQUIRED — применяется с первой пробы.

#### Scenario: Подтверждённая утечка

- **WHEN** проба дала leak-кандидата и повторная проба через 2–3 с снова дала leak
- **THEN** фиксируется переход в Leak

#### Scenario: Разовый ложняк

- **WHEN** проба дала leak-кандидата, а повторная проба через 2–3 с дала protected
- **THEN** переход в Leak не происходит

### Requirement: Мониторинг активен с запуска

Система SHALL начинать мониторинг сразу при запуске приложения (немедленная проба на старте) и SHALL выполнять немедленную пробу при появлении любой сети.

#### Scenario: Старт приложения

- **WHEN** приложение запустилось и мониторинг включён
- **THEN** немедленно выполняется проба и по её результату устанавливается состояние

#### Scenario: Появилась сеть

- **WHEN** сеть стала доступна после отсутствия
- **THEN** немедленно выполняется проба

### Requirement: Статус VPN-клиента не используется как детектор

Система SHALL NOT использовать статус VPN-клиента (например, `scutil --nc status`) как критерий защищённости. Допустимо показывать его в UI как справочную информацию.

#### Scenario: VPN-клиент сообщает «Подключено» при реальной утечке

- **WHEN** VPN-клиент считает соединение активным, но маяк видит чужой egress
- **THEN** система классифицирует состояние по маяку (leak-кандидат), игнорируя статус клиента

### Requirement: РУ-маяк — автоопределение прямого IP

Система SHALL периодически запрашивать «прямой IP» текущей сети у РУ-маяка (конфигурируемые URL; домен обязан быть в зоне `.ru`): основной `https://yandex.ru/internet/api/v0/ip` (JSON-строка `"<ip>"`), резервный `https://2ip.ru` (text/plain, требуется curl-подобный User-Agent). Ответ SHALL валидироваться как IP-адрес (v4/v6), иначе отбрасывается. Запрос выполняется при старте, при каждом событии сети и далее раз в `ruBeaconRefreshSeconds` (300 с). Полученный прямой IP образует динамическую часть `FORBIDDEN_EGRESS` и живёт до следующей смены сети.

#### Scenario: Прямой IP получен

- **WHEN** РУ-маяк вернул валидный IP-адрес
- **THEN** адрес становится динамической частью `FORBIDDEN_EGRESS` и немедленно запускается свежая проба foreign-маяка

#### Scenario: Невалидный ответ РУ-маяка

- **WHEN** тело ответа РУ-маяка после разбора не является IP-адресом
- **THEN** результат отбрасывается, динамическая запись не обновляется

#### Scenario: Основной РУ-маяк недоступен

- **WHEN** основной РУ-маяк не ответил за таймаут 6 с
- **THEN** выполняется запрос к резервному РУ-маяку

### Requirement: Guard от РУ-маяка, прошедшего через VPN

Система SHALL NOT добавлять ответ РУ-маяка в denylist, если он совпал с текущим protected-egress (`warp=on`): это означает, что `.ru` не в сплите и запрос ушёл через VPN. В журнал SHALL записываться предупреждение.

#### Scenario: РУ-маяк вернул protected-egress

- **WHEN** ответ РУ-маяка равен текущему egress-IP при состоянии Protected
- **THEN** запись в denylist не добавляется, в журнал пишется предупреждение «РУ-маяк прошёл через VPN, сплит не работает?»

### Requirement: Сбой РУ-маяка некритичен

Сбой РУ-маяка SHALL NOT менять состояние детектора: динамическая запись denylist просто устаревает, в UI отображается её давность.

#### Scenario: РУ-маяк полностью недоступен

- **WHEN** оба РУ-маяка не отвечают
- **THEN** состояние детектора не меняется, давность прямого IP в UI растёт

### Requirement: Статическая часть FORBIDDEN_EGRESS

Система SHALL поддерживать редактируемый пользователем статический список запрещённых egress-IP (серверы инфраструктуры). Egress с любого адреса списка SHALL классифицироваться как leak-кандидат независимо от прочих признаков. Список SHALL быть пустым по умолчанию: выходные узлы у каждого пользователя свои, а приложение раздаётся другим людям (осознанное отклонение от §13 SPEC.md, где список предзаполнен адресами автора).

#### Scenario: Утечка через сервер инфраструктуры

- **WHEN** egress-IP пробы совпал с адресом из статического списка
- **THEN** результат — leak-кандидат с диагнозом «цепочка вышла напрямую с сервера <ip>» (отвал WARP на выходном узле)

#### Scenario: Первый запуск у нового пользователя

- **WHEN** приложение запускается впервые
- **THEN** статический список запрещённых egress пуст, и классификация опирается только на `warp`/`EXPECTED_IPS` и динамический прямой РУ-IP
