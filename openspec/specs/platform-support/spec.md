# platform-support

## Purpose

Диапазон версий macOS, на которых приложение и его привилегированный helper обязаны работать: минимальный порог запуска, запрет на использование API новее этого порога и автоматическая проверка обеих границ диапазона перед мержем.

## Requirements

### Requirement: Минимальная поддерживаемая версия macOS

Приложение и helper SHALL запускаться на macOS 15.7 и новее. Deployment target обоих таргетов SHALL быть `15.7`; собранные бинари (приложение и вложенный `Contents/MacOS/<label>.helper`) SHALL сообщать `minos 15.7` в `LC_BUILD_VERSION`. Поддерживаемый диапазон — от 15.7 до текущей macOS 26.x включительно; сборка при этом ведётся против актуального SDK (26.x), а не против SDK минимальной версии.

Порог SHALL быть равен версии, которая фактически проверяется (сборочная машина и образ CI), а не самой низкой теоретически совместимой: заявленная поддержка означает проверенную поддержку. Снижение порога допустимо, когда появится машина, на которой более низкая версия проверяется.

#### Scenario: Запуск на Sequoia

- **WHEN** установленная копия приложения открывается на macOS 15.7.8
- **THEN** приложение запускается и живёт в строке меню — macOS не отклоняет его как «требующее более новой версии»

#### Scenario: Порог зашит в оба бинаря

- **WHEN** собрана Release-конфигурация
- **THEN** `minos` равен 15.7 и у бинаря приложения, и у бинаря helper внутри бандла, а `LSMinimumSystemVersion` в `Info.plist` — 15.7

#### Scenario: Работа на текущей macOS не теряется

- **WHEN** та же сборка запускается на macOS 26.x
- **THEN** поведение идентично прежнему: детектор, helper, переключение групп и UI работают без изменений

### Requirement: Универсальный артефакт

Приложение и helper SHALL собираться универсальными — со слайсами `arm64` и `x86_64`. Набор архитектур SHALL задаваться явно, а не наследоваться от «стандартного» набора текущего Xcode: поддержка Intel сворачивается, и потеря слайса иначе проявится не ошибкой сборки, а неработающим приложением на целевой машине.

#### Scenario: Запуск на Intel-машине

- **WHEN** собранный на Apple Silicon бандл перенесён на Intel-Mac из поддерживаемого диапазона macOS
- **THEN** приложение и helper запускаются нативно, без Rosetta

#### Scenario: Слайс не теряется молча

- **WHEN** очередной Xcode перестаёт включать `x86_64` в стандартный набор архитектур
- **THEN** сборка проекта продолжает давать оба слайса, потому что набор задан явно

### Requirement: Никаких API новее минимального порога

Исходники SHALL NOT использовать системные API, недоступные на минимальной поддерживаемой версии, без явного `@available`/`#available`-гейта с определённым поведением на старой ОС. Нарушение SHALL проявляться как диагностика availability при сборке («is only available in macOS … or newer»), а не как отказ на машине пользователя.

#### Scenario: Чистая сборка на минимальном пороге

- **WHEN** проект собирается с deployment target, равным минимальной поддерживаемой версии
- **THEN** сборка проходит без ошибок и без предупреждений availability

#### Scenario: Попытка ввести API новее порога

- **WHEN** в код добавлен вызов API, доступного только с более новой macOS, без гейта
- **THEN** сборка падает с ошибкой availability, и изменение не проходит проверки

### Requirement: Проверка обеих границ диапазона в CI

CI SHALL прогонять сборку и тесты на обеих границах поддерживаемого диапазона: на образе, версия которого не ниже минимальной поддерживаемой macOS и не выше следующей мажорной, и на образе с текущей. Обе проверки SHALL использовать ту же мажорную версию Xcode и SDK, что и локальная сборка разработчика, — иначе проверяется не та конфигурация, что поставляется. Обе проверки SHALL быть обязательными для мержа в `main`.

#### Scenario: Проверки на PR

- **WHEN** открыт pull request
- **THEN** запускаются две проверки — на минимальной поддерживаемой macOS и на текущей — и мерж возможен только когда обе зелёные

#### Scenario: Регресс совместимости ловится до мержа

- **WHEN** изменение использует API новее минимального порога
- **THEN** проверка на минимальной macOS падает, и регресс не попадает в `main`

#### Scenario: На минимальной ОС доступна только более старая минорная версия Xcode

- **WHEN** на образе с минимальной поддерживаемой macOS новейший установленный Xcode нужной мажорной версии старше того, на котором ведётся разработка
- **THEN** проверка идёт на нём, и код обязан собираться этой версией: расхождения минорных версий тулчейна строже там, где никто не собирает вручную

### Requirement: Раздельные требования к запуску и к сборке

Документация SHALL указывать требования к среде двумя раздельными списками: для **запуска** (минимальная поддерживаемая macOS) и для **сборки** (версия macOS и допустимые версии Xcode, дающие требуемый SDK). Требование к сборочной машине SHALL NOT выдаваться за требование к машине пользователя.

#### Scenario: Пользователь на минимальной macOS

- **WHEN** пользователь сверяет свою систему с документацией перед установкой
- **THEN** он видит порог запуска, не завышенный требованиями сборочной машины

#### Scenario: Сборка на минимальной macOS

- **WHEN** разработчик собирает проект на минимальной поддерживаемой macOS
- **THEN** документация называет конкретные версии Xcode, которые там ставятся и дают нужный SDK
