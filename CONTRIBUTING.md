# Как вносить изменения

## Коротко

1. `main` защищён: изменения попадают только через pull request с зелёным CI —
   обе проверки, «Тесты (macOS 26)» и «Тесты (macOS 15)», по границам
   поддерживаемого диапазона; прямые пуши и force-push запрещены даже владельцу.
2. Проект разрабатывается по **Spec-Driven Development** через
   [OpenSpec](https://openspec.dev): любое изменение логики
   идёт через openspec-процесс и обновляет спеки. Код без обновлённых спек —
   неполное изменение.
3. Никаких реальных IP-, MAC-адресов и ключей в коммитах — только заполнители
   (см. «Личные данные»).

## Spec-Driven Development

Источник истины по поведению системы — спеки в `openspec/specs/<capability>/spec.md`
(требования в формате SHALL + сценарии). Их девять: детектор egress, state machine,
управление rule groups, эскалация, журнал, уведомления, настройки, онбординг,
меню-бар UI. Завершённые изменения лежат в `openspec/changes/archive/`.

[SPEC.md](SPEC.md) — исходное ТЗ проекта; на его §-нумерацию ссылаются комментарии
в коде (например, «таблица §8.1»), поэтому он сохраняется как справочник. Актуальное
поведение системы описывают спеки в `openspec/`.

### Процесс изменения логики

Каждое изменение поведения проходит четыре шага (слэш-команды Claude Code из
`.claude/commands/opsx/`, под капотом — [OpenSpec CLI](https://openspec.dev)):

1. **`/opsx:propose`** — создать change: `proposal.md` (что и зачем), дельты спек
   `specs/<capability>/spec.md` (какие требования добавляются/меняются),
   `design.md` (как), `tasks.md` (шаги реализации).
2. **`/opsx:apply`** — реализация по tasks. Новая логика — вместе с тестами:
   таблицы поведения Domain покрываются построчно.
3. **`/opsx:sync`** — перенести дельты в основные спеки `openspec/specs/`.
4. **`/opsx:archive`** — после завершения переместить change в
   `openspec/changes/archive/`.

**Что считается изменением логики:** детектор и классификатор, state machine,
политика реакции, эскалация, контракт helper, поведение настроек, онбординга,
уведомлений и UI.

**Что можно без openspec-процесса:** опечатки, документация, CI, скрипты,
рефакторинг без изменения поведения.

## Pull request

- Ветка от `main` → PR → мерж после зелёных «Тесты (macOS 26)» и «Тесты (macOS 15)».
  Ревью не требуется, CI обязателен; ветка должна быть актуальной относительно `main`.
- Прогнать локально перед пушем:

  ```bash
  xcodegen generate && xcodebuild -project LittleSnitchVPNCompanion.xcodeproj -scheme LittleSnitchVPNCompanion -configuration Debug test
  ./Scripts/check-domain-purity.sh
  ```

- `.xcodeproj` не хранится в git — таргеты и настройки правятся в `project.yml`.
- `Domain/` — чистый Swift без Apple-фреймворков; проверяется
  `check-domain-purity.sh` и в CI.

## Личные данные

В репозиторий не коммитятся реальные адреса — ни в код, ни в доки, ни в тесты,
ни в макеты (`design/app.pen` — обычный JSON, его тоже проверять):

- IP-примеры — только документационные диапазоны RFC 5737: `192.0.2.0/24`,
  `198.51.100.0/24`, `203.0.113.0/24` (исключения — служебные адреса вроде
  `1.1.1.1` и частные диапазоны).
- MAC-примеры — синтетические locally-administered (`02:…`).
- Реальные адреса VPN-инфраструктуры живут только в локальных настройках
  приложения (`defaults`), ключи и сертификаты — только в Keychain.
