# Выпуск релиза

Проект распространяется готовым бандлом во вложениях GitHub Releases. Артефакт
подписан самоподписанным сертификатом, и на этом держится вся защита
привилегированного демона: helper пускает к себе только клиента, подписанного
тем же сертификатом. Поэтому релиз собирается локально, а каждый шаг ниже
существует, чтобы в публичный тег не уехала сборка, у которой эта связь
нарушена.

**Область навыка:** `main` готов → версия → сборка → проверки → черновик →
публикация. Ветка, PR, ожидание CI и мерж — обычная работа по
[CONTRIBUTING.md](../../../CONTRIBUTING.md), навык их не ведёт.

## Шаг 1. Убедиться, что выпускать есть что и откуда

Тег релиза обязан встать на тот же коммит, что и `origin/main`: релизится то,
что прошло обе обязательные проверки CI, а не то, что случайно оказалось в
рабочем каталоге.

```bash
git fetch --tags origin && git log -1 --format='%H %s' && git rev-parse origin/main
```

Если `HEAD` не совпадает с `origin/main` — перевести туда рабочий каталог.
В worktree `git checkout main` не сработает: ветка занята основным каталогом
репозитория, поэтому нужен detached-переход.

```bash
git checkout --detach origin/main
```

Дальше — что CI на этом коммите зелёный:

```bash
gh run list --commit "$(git rev-parse HEAD)" --json name,conclusion,status
```

Команда отдаёт прогоны воркфлоу целиком (`name: "CI"`), а не отдельные джобы —
этого достаточно: прогон становится `success` только когда зелены обе
обязательные проверки, «Тесты (macOS 26)» и «Тесты (macOS 15)». Требуется
`status: completed` и `conclusion: success` у каждого прогона на этом коммите.
Если они ещё идут — дождаться; если красные — релиз не собирать и сказать об
этом прямо.

Остальные предпосылки (чистое рабочее дерево, запушенный `HEAD`, свободный тег,
наличие сертификата) проверяет сам `Scripts/release.sh` — дублировать их
вручную не нужно.

## Шаг 2. Посчитать версию

Собрать материал одной командой — она приносит одни и те же факты в одном и том
же виде, чтобы один набор изменений не получал разный вердикт в разные дни:

```bash
./.claude/skills/release/scripts/collect-evidence.sh
```

Скрипт печатает: последний тег, коммиты после него, затронутые каталоги,
изменённые исходники артефакта, сводку по `openspec/` (новые и удалённые
capability, прирост и убыль строк `SHALL`, архивированные changes) и отдельным
блоком — сигналы, за которыми может стоять ломающее изменение. Решение он не
принимает; решаешь ты по таблице ниже.

### Сначала — есть ли что публиковать

Релиз выкладывает собранный бандл, а не историю репозитория. Поэтому первым
делом смотри блок `ИСХОДНИКИ АРТЕФАКТА`: если там «не менялись», скрипт на этом
и останавливается — и правильно делает. Ни один файл, попадающий в бандл, не
изменился, новая сборка отличалась бы от прошлой только строкой версии, и
выпускать нечего.

Так бывает, когда изменились спеки, документация, CI, тесты или макеты. Спеки
без кода означают, что change ещё не реализован; всё остальное к содержимому
бандла отношения не имеет. В обоих случаях релиз не собирать, а сказать
пользователю, что именно изменилось и почему это не тянет на выпуск. Если он
настаивает — это его решение, но по умолчанию правильный ответ «пока нечего».

### Таблица бампа

Дальше — только когда исходники артефакта изменились.

| Что видно в материале | Бамп |
|---|---|
| Порог macOS **поднят**; удалена или переименована настройка приложения; удалена capability или снято требование `SHALL`; сменился сертификат подписи, bundle id или `machServiceName` | **MAJOR** |
| Новая capability; добавлены требования `SHALL`; новая настройка, экран, уведомление или debug-рычаг; порог macOS **понижен** | **MINOR** |
| Исправления в рамках существующих требований; рефакторинг; правки сборочных настроек без смены поведения | **PATCH** |

Срабатывает несколько строк — берётся самая крупная. Документация, CI, `Scripts/`
и тесты сами по себе бамп не задают: они едут попутчиками к тому, что изменилось
в коде, и на размер шага не влияют.

Почему смена сертификата, bundle id или `machServiceName` — мажор, хотя код
может не измениться вовсе: установленный helper построил свой XPC-requirement
из прежней подписи и новое приложение к себе не пустит. Обновление «поверх» не
сработает, пользователю придётся сносить демона руками. Это ровно тот случай,
для которого мажор и существует.

Почему направление сдвига порога macOS решает всё: понижение расширяет круг
поддерживаемых машин и ничего не ломает, повышение отсекает тех, кто уже
пользуется приложением. Скрипт печатает обе стороны (`26.0 → 15.7`), направление
читается глазами.

Если материал неоднозначен — например, спека изменена, но непонятно, добавилось
обещание или уточнилась формулировка, — прочитать сам дифф:

```bash
git diff "$(git describe --tags --abbrev=0)..HEAD" -- openspec/specs/
```

Когда после этого сомнение осталось, не выбирай молча: покажи пользователю оба
прочтения с их последствиями и спроси. Ошибка в сторону завышения дешевле — но
она тоже врёт пользователю о характере изменений, так что угадывать не надо.

Вердикт озвучить до сборки, вместе с обоснованием и получившимся номером:

```
Вердикт: MINOR → 1.1.0
Причина: новое требование в capability egress-detection; ломающих сигналов
и сдвига порога macOS нет.
```

## Шаг 3. Собрать и получить черновик

```bash
./Scripts/release.sh 1.1.0
```

Скрипт делает всё сам: `xcodegen`, чистая сборка Release с нужным
`MARKETING_VERSION`, проверки артефакта, упаковка `ditto` и черновик релиза с
вложением и инструкцией по установке в заметках.

Не обходить его и не собирать вручную. Его проверки — то единственное, что
отделяет релиз от ad-hoc-сборки, у которой XPC-requirement выродился в проверку
одного `identifier` и к root-демону проходит любой процесс с нужным bundle id.
Скрипт ловит это тем, что у ad-hoc подписи нет строки `Authority` вовсе.

Сборка идёт несколько минут и печатает предупреждения `xcodebuild` про
CoreSimulator — к релизу они отношения не имеют. Значение имеет только то, что
скрипт дошёл до строки про черновик.

## Шаг 4. Показать черновик и спросить

```bash
gh release view v1.1.0 --json isDraft,tagName,targetCommitish,assets,body
```

Показать пользователю: тег, целевой коммит (он обязан совпадать с `origin/main`),
имя и размер вложения, из чего состоят заметки.

Дальше — остановиться и спросить, публиковать ли. Публикация выкладывает релиз
наружу и создаёт тег в репозитории; GitHub умеет делать опубликованные релизы
неизменяемыми, и откат такого шага стоит куда дороже, чем один вопрос. Черновик
же не виден никому и ничего не стоит выбросить.

## Шаг 5. Опубликовать и проверить

```bash
gh release edit v1.1.0 --draft=false --latest
```

Убедиться, что получилось то, что задумано, и сказать это пользователю ссылкой:

```bash
gh release view v1.1.0 --json isDraft,tagName,publishedAt && git fetch --tags origin && git rev-parse v1.1.0
```

Тег должен указывать на тот же коммит, что и `origin/main`. Шильдик версии в
README подтянется сам — он читает `releases/latest`, править README не нужно.

## Грабли

**Первый релиз.** Если тегов нет вовсе, скрипт материала так и скажет: считать
не от чего, номер назначает человек.

**Выпускать нечего.** Два разных случая, и оба скрипт материала распознаёт сам:
`HEAD` совпадает с последним тегом, либо коммиты есть, но ни один не тронул
исходники артефакта. В обоих не выдумывай пустой бамп — объясни, что изменилось
и почему это не меняет то, что получает пользователь.

**Черновик уже есть.** `Scripts/release.sh` отказывается работать, если релиз с
таким тегом существует. Незавершённый черновик от прошлой попытки видно в
`gh release list`; его либо публикуют, либо удаляют (`gh release delete`), и
только потом собирают заново.
